= Migration
:description: Migrating from Weld, Quarkus ArC, or OpenWebBeans to Vauban.

[CAUTION]
====
Vauban is at `{project-version}`. Real application migration is premature until the TCK coverage is consolidated (see xref:tck.adoc[TCK status]). This page documents model mappings and known pitfalls to prepare the transition.
====

[.lead]
Vauban implements the CDI 4.1 Lite profile. Migrating therefore implies dropping Full-profile features when used (runtime portable extensions, `@ConversationScoped`, passivation, application-level EL).

== From Quarkus ArC

ArC shares Vauban's build-time philosophy. The port is conceptually direct; gaps are mostly tooling.

[cols="2,2,3"]
|===
| ArC | Vauban | Note

| Full build-time CDI
| Full build-time CDI
| Identical model. No paradigm shift on the application side.

| Bytecode generation via Gizmo
| Bytecode generation via Class-File API (JEP 484)
| No ASM. Output is compatible with any JVM 25+.

| `@io.quarkus.arc.Unremovable`
| No direct equivalent
| Vauban currently only removes unreferenced beans. // TODO@user: confirm whether a similar annotation is planned.

| `@io.quarkus.arc.profile.IfBuildProfile`
| No equivalent
| Build-time profiling is the responsibility of the xref:vidocq::index.adoc[Vidocq Runtime] layer.

| Quarkus Dev Mode
| `vauban-junit` + standard Maven cycle
| Vauban has no dedicated Dev Mode.

| `@Startup`
| `@Observes @Initialized(ApplicationScoped.class)`
| Standard CDI pattern.
|===

== From Weld

Weld implements the Full profile; some features used by historical applications have no Lite equivalent.

Key differences:

* **No runtime `AnnotatedType` lookup** — Vauban resolves everything at compile time. Code that calls `BeanManager.createAnnotatedType(Class)` must be rewritten as a Build Compatible Extension.
* **No runtime `BeforeBeanDiscovery` / `AfterBeanDiscovery`** — replaced by the BCE phases `@Discovery` / `@Enhancement` / `@Registration` / `@Synthesis` / `@Validation`.
* **No portable extensions** — the `Extension` interface is not loaded via `ServiceLoader` at runtime. Migrate every extension to a compile-time BCE.
* **No `@ConversationScoped`** — refactor to `@SessionScoped`, which Vauban supports with `vauban-webcontexts` when Foy serves the requests (xref:usage.adoc#web-contexts[Web contexts]), or to an explicit application mechanism.

== CDI 4.1 Lite pitfalls

Lite-profile specifics worth knowing before migrating:

* **`@Decorator`** — not supported. Decorators belong to CDI Full, not to Lite: Vauban applies none, and `BeanManager.resolveDecorators` returns an empty list. Use an interceptor, or composition, until CDI Full support lands (see BUG-20261116-02 in link:{repo-vauban}/src/branch/main/BUG.md[BUG.md]).
* **`@Specializes`** — not supported. Refactor as composition or a prioritised `@Alternative`.
* **`@Alternative` + `@Priority`** — supported; check existing priorities.
* **Producer methods with `@Disposes`** — supported.
* **`@Inject` field on a normal scope** — correctly resolves the client proxy (see fix VAU-INJ-001 in link:{repo-vauban}/src/branch/main/BUG.md[BUG.md]).
* **`InjectionPoint` metadata** — supported.

== Upgrading from Vauban {release-version}

What an application built on Vauban `{release-version}` may notice on the `{project-version}` line. The full list is in xref:whats-new.adoc[What's new].

* **A static observer method of a superclass is not inherited.** A bean no longer gets the static observer methods of its superclasses, as CDI 4.1 says. A static observer of a superclass that is no bean is no longer called; declare it on a bean class, or make it non-static. One of a superclass that is a bean is now called once per event. This departs from Weld: Weld 5.1.7 (`EnhancedAnnotatedTypeImpl`) registers an inherited static observer on every subclass bean, even when the superclass is no bean. Vauban follows CDI 4.1, sections 4.2 and 10.4. An application that moves from Weld and counts on such an observer declares it on a bean class (BUG-20261118-51).
* **`@Registration`, `@Synthesis` and `@Validation` no longer see what `@Enhancement` removed.** An extension that removes an annotation in `@Enhancement` and read it back in a later phase no longer finds it there. The build still does not freeze such an extension: it runs at each start (BUG-20261118-45).
* **`@Registration(types = Object.class)` also gets the built-in beans.** A `BeanInfo` parameter is now given the built-in beans too; their `declaringClass()` is their interface, in a `jakarta.` package. It is no longer given, at start, a class of the deployment that is no bean. An extension that records every bean it gets filters the built-in ones by their declaring class. `InvokerFactory.createInvoker` throws a `DeploymentException` for every invoker it may not build: of a bean that is no managed bean, a producer included, of an interceptor, a constructor, a private method, a method of `Object` or of another class. It threw an `IllegalStateException` (BUG-20261117-06).
* **`@Registration` matches bean types exactly.** A `@Registration` method is called for a bean whose bean types contain one of its `types`; a `@Typed` bean is no longer given for a supertype of the types it names (BUG-20261118-43).
* **`@Enhancement` runs once, on the extension's own instance.** At start, an `@Enhancement` method is called once for each type it matches, no longer twice, and on the instance the extension's `@Discovery`, `@Registration` and `@Synthesis` methods run on: a field it sets in `@Enhancement` is now seen by the later phases. An extension that counted its calls, or that relied on a second call, sees one (BUG-20261117-08).
* **`@Registration` gets the producers of primitive and array types.** A `@Registration` method whose `types` holds `int` or `Integer` is now also called for a producer of `int`, and one whose `types` holds `String[]` for a producer of `String[]`, and the like. Such a producer has no other bean type than its type and `Object`: `Number` or `Serializable` does not match it (BUG-20261117-11).
* **An `ObserverInfo` no longer answers `null`.** A `@Registration` method with an `ObserverInfo` parameter gets the observer method, its event parameter, the bean that declares it and the observed qualifiers; `isSynthetic()` is `true` for a synthetic observer (BUG-20261117-09).
* **A `@Registration` method sees the injection points of an interceptor.** An `InterceptorInfo`, and a `BeanInfo` of an interceptor that `@Registration(types = Object.class)` gives, now has the bean types, the qualifiers (`@Any`, `@Default`) and the injection points of its class. An extension that acts on each injection point it is given now acts on those of the interceptors too (BUG-20261117-04).
* **A `BeanInfo` no longer answers `null` for a producer's member.** A `@Registration` method gets the producer method or field, the disposer and the stereotypes of a bean; an extension that tested them for `null` now takes the other branch (BUG-20261117-13).
* **A raw bean type satisfies only the parameterizations CDI allows.** A producer of a raw `Foo`, `@Produces Foo foo()` with `Foo<T>` generic, satisfies `@Inject Foo<Object>`, and no other `Foo<X>`, nor `Foo<?>` (CDI 4.1, 5.2.4). Such an injection point fails the build when `Foo` is a class; when it is an interface, the build warns and the start throws a `DeploymentException`. Give the producer its parameterized return type, `@Produces Foo<Integer> foo()`, or inject the raw type, `@Inject Foo`.
* **A raw injection point or `select` no longer finds a bean of a bounded generic class.** A bean of `Repo<T extends Number>` no longer satisfies a raw `@Inject Repo` nor `VaubanContainer.select(Repo.class)`; `BeanManager.getBeans(Repo.class)` already did not find it. A bounded generic `@Dependent` Cassini resource or provider fails at request time with `Not managed by Vauban`. Inject or look up a parameterization within the bound, `Repo<Integer>`, or declare the type variable unbounded.
* **An observer's, a disposer's, a producer method's or an initializer's parameter, or an `@Inject` field, of a type variable is a definition error.** A parameter besides the event parameter, besides the disposed one, of a producer method, of an initializer or of a bean constructor, or an `@Inject` field, the field inherited or not, typed by a type variable of the bean class, `T gadget` in `WidgetFactory<T extends Gadget>`, makes the build warn and the start throw a `DefinitionException`, `Injection point has type variable type T: ...` (CDI 4.1, 5.2.3). Declare the parameter of its bound, `Gadget gadget`, or move the method to an abstract or `@Vetoed` class whose subclass gives the type variable a class: such a class's initializer is no longer refused. The rule applies to a bean as bean discovery decides: a concrete class without a bean-defining annotation is none, and a bean that inherits its initializer gives the type variable its class. A bean that inherits an initializer and leaves its parameter a type variable of its own, `Sub<T> extends VetoedSetter<T>`, now fails the start: give the superclass a type argument.
* **A non-contextual injection point follows the strict rule.** An instance injected through an `InjectionTarget` or created by `Unmanaged` no longer gets a bean of the erased class of a parameterized injection point no bean satisfies: a producer of a raw `Foo` no longer satisfies its `@Inject Foo<Integer>`, and the injection throws an `UnsatisfiedResolutionException`. Give the producer its parameterized return type. The same holds for its qualifiers: `@Inject @Red Knob` no longer gets the `@Default Knob`. Deploy a bean with the qualifier, or drop it.
* **An inherited observer's parameters are checked at start.** A bean that inherits an observer whose parameter no bean satisfies, or more than one, fails the start with a `DeploymentException`, where the first event failed; one that leaves the parameter a type variable fails with a `DefinitionException`. Give the parameter a bean, or the bean class a type argument for the superclass's type variable.
* **The build resolves the parameters of an inherited or a static observer.** An application whose inherited or static observer has a parameter no bean satisfies, or more than one does, now fails the build where it failed the start. Fix the deployment as the error says, or give the parameter a qualifier that selects one bean (BUG-20261118-11).
* **A class an extension adds through `ScannedClasses` is checked like a bean class.** An application whose extension adds a class that breaks a class-level definition rule, an injection point of a type variable say, now fails the start with a `DefinitionException` (BUG-20261118-12).
* **The build writes a class for each invoked method.** An application whose extension builds invokers finds `<Bean>$$VaubanInvoker$<method>$<hash>` classes next to its bean classes, written by the annotation processor or by `vauban:generate`, and its synthetic metadata records those invokers with a `G:` value that a Vauban runtime older than this line cannot read: build and run the application with the same Vauban version.
* **An extension builds an invoker of a bean the build compiles.** An extension that builds an invoker in `@Registration` no longer fails the compilation of the application whose beans it invokes, and the build now checks that invoker's argument lookups: an unsatisfied or ambiguous one fails the build, as it fails the start (BUG-20261117-48).
* **An invoker's instance lookup finds a target bean that has a qualifier.** A call that threw `UnsatisfiedResolutionException` because its target bean has a qualifier and no `@Default`, or because `@Typed` leaves its class out of its bean types, now reaches the bean (BUG-20261117-38).
* **An invoker may look up every built-in bean the call serves.** An extension whose invoker looks up the `BeanContainer`, a `Provider`, the `RequestContextController` or the `InjectionPoint` no longer fails the build or the start (BUG-20261117-44).
* **An extension that runs at start may look up the synthetic beans of the others.** A deployment that freezes some extensions, or holds an archive the processor processed, no longer fails its start when an extension that runs at start looks up a synthetic bean of the others (BUG-20261117-45).
* **An interceptor may inject `@Intercepted Bean<?>` and its own `Interceptor`.** Such an interceptor no longer fails the compilation, the start or a frozen start with "Illegal injection of built-in metadata type" (BUG-20261117-41).
* **The bean metadata beans of CDI Lite.** A bean that injects its own `Bean`, or an interceptor that injects its own `Interceptor` or `@Intercepted Bean<?>`, is now created; it failed with `UnsatisfiedResolutionException` at its first use (BUG-20261117-47).
* **An interceptor instance for each intercepted instance.** An interceptor that keeps state now sees one intercepted instance only: two intercepted beans a constructor injects, or that `BeanManager.getReference` creates with one creational context, no longer share it (BUG-20261118-36).
* **A generic class with a scope an extension added fails the start.** A build compatible extension that adds `@RequestScoped`, `@ApplicationScoped` or `@Singleton` to a generic class at `@Enhancement` makes the build warn and the start throw a `DefinitionException`, `Managed bean ...Resource has type parameters and is not @Dependent: @...` (CDI 4.1, 3.1), as on Weld. Have the extension leave a generic class `@Dependent`, or make the class not generic. With Cassini, take the version with CASSINI-065, whose `CassiniScopeExtension` gives a generic `@Path` class `@Dependent`; an older one fails the start of an application with a scope-less generic resource.
* **A producer of an inner class of a generic class.** `@Inject Holder<String>` on a producer of `Outer<String>.Inner<Integer>`, where `Inner<I> implements Holder<O>`, is unsatisfied at build and at start until BUG-20261117-21 is fixed. The exact messages are in xref:whats-new.adoc[What's new].
* **Recompile with the matching processor.** The generated classes live in your archive, so an archive compiled by an earlier processor keeps its old client proxies and intercepted subclasses until it is recompiled. See xref:internals.adoc#intercepted-methods[Which methods the intercepted subclass covers].
* **Run `vauban:generate` again on what it processed.** The client proxies it wrote skipped a method that has a compiler bridge, such as `String get()` of a `Supplier<String>`, and a call to it ran on the proxy (BUG-20261117-49), and a bridge javac adds to reach a superclass method of another erasure, through which a call typed by an interface ran on the proxy (BUG-20261118-17). A proxy the container generates at run time is right as soon as the container is upgraded. See xref:whats-new.adoc[What's new].
* **A normal-scoped bean that inherits a `final` method is refused as its class.** A bean whose superclass declares a `final` method, neither `private` nor `static`, package-private ones of another package included, used to start when the superclass was no bean or came from a library: the annotation processor now fails the build, and the container the deployment, where the bean is injected as that class or a class between it and the method; a lookup of that type throws `UnproxyableResolutionException`. Injected or looked up as an interface, the bean works as before. A call of that method used to run on the client proxy, not on the bean. Remove the `final`, inject an interface the bean implements, or make the bean `@Dependent`. See xref:whats-new.adoc[What's new].
* **The client proxy of a bean whose class has a `final` method no longer extends the bean class.** It extends the nearest class above the `final` method that has none, often `Object`, and implements the bean's interfaces, so a call through one of them reaches the bean (BUG-20261118-20). Code that tests the proxy with `instanceof` against the bean class, or casts it to that class, now sees `false` or a `ClassCastException`; such a bean is only proxyable as its interfaces or a class above the `final` method. Code that reads the bean class from the proxy's superclass, to find its annotations, now asks `io.vidocq.vauban.api.ClientProxyClass.beanClassOf(proxy.getClass())`, which answers on every proxy. A lookup as an interface the proxy cannot implement, package-private in another package, now throws `UnproxyableResolutionException`. The annotation processor emits that proxy as bytecode, and no build step retargets its constructor onto a `(ProxyLink)` one.
* **A final normal-scoped bean class is accepted as its interfaces.** Injected or looked up as an interface it implements, it now starts and works, where it used to throw `UnproxyableResolutionException` or fail the build; injected as its own class, it still fails the deployment, and a lookup of that class throws (BUG-20261118-21).
* **A normal-scoped producer of a parameterized type now works.** A producer of `Supplier<String>` or `Box<Integer>` injected as its type used to fail with a `ClassCastException` or `UnproxyableResolutionException`; it now gets the proxy of its raw type, which the processor and `vauban:generate` write at build. A producer of a JDK class with package-private methods, such as `ArrayList<String>`, is now judged as `ArrayList` and refused, with a message that names the remedy: produce an interface type, or use `@Dependent` or `@Singleton`. CDI 4.1 §3.10 allows it, and Weld deploys it; this is a Vauban limitation that departs from Weld (BUG-20261117-18, BUG-20261118-24).
* **A normal-scoped producer of a class with a `final` method is refused, bridge or not.** Where the method has a compiler bridge, `public final String get()` of a `Supplier<String>` say, `vauban:generate` and the dependency enhancer used to write a proxy that could not override it, and the start accepted the producer. Now `vauban:generate` warns `Producer of <class> is not build-time proxyable (FINAL_VIRTUALS)`, and a start that must generate the proxy in the producer's package fails with a `DeploymentException`. Remove the `final`, produce an interface the class implements, or make the producer `@Dependent`. See xref:whats-new.adoc[What's new].
* **More beans are intercepted.** An interceptor binding on an interface default method the bean does not override now applies. A `final` bean class, or a bean with a `final` method, bound only that way now fails with a `DeploymentException`. An unproxyable intercepted bean is reported as a `DeploymentException` in every case, with why it is intercepted, where a `final` class used to raise a `DefinitionException`. See xref:internals.adoc#unproxyable-intercepted[unproxyable intercepted beans].
* **`@AroundInvoke` no longer wraps `@PostConstruct` / `@PreDestroy`.** A class-level `@Transactional`, `@Retry` or `@Timed` no longer opens a transaction, retries or records a metric around the lifecycle callbacks.
* **Interceptors see the inherited declaration.** `InvocationContext.getMethod()` returns the superclass or interface method a call runs, not the `$$super$` bridge, and `getInterceptorBindings()` includes that declaration's bindings.
* **Default name of a nested bean class.** `@Named` without a value on `Outer.ReportService` names the bean `reportService`, no longer `outer$ReportService`. Update any lookup by the old name. See xref:usage.adoc#qualifiers[Qualifiers].
* **Disposers.** A producer's disposer runs once, no longer twice, and its qualified parameters resolve on their qualifiers. See xref:usage.adoc#producers-and-disposes[Producers and `@Disposes`].
* **`beans.xml` discovery mode.** With `SeContainerInitializer` default discovery, an empty `beans.xml`, or one declaring `annotated`, now discovers only classes with a bean-defining annotation; it used to make every concrete class a bean. Declare `bean-discovery-mode="all"` to keep the old behaviour, or annotate the classes. See xref:se.adoc#bean-archives[Default discovery: bean archives].
* **Injection failures propagate.** A failed field injection reaches the caller instead of leaving the field `null`. See xref:internals.adoc#boot-failures[Failures are reported, not swallowed].
* **Supertypes keep their type arguments.** In an extension, `ClassInfo.superClass()` and `superInterfaces()` give a parameterized type for a supertype declared with type arguments, where they gave a class: `asClass()` on it now throws. Read its class with `asParameterizedType().genericClass()`, or use `superClassDeclaration()` and `superInterfacesDeclarations()`. An interface's `superClass()` is `null` at start, as in the processor. A wildcard `?` has `java.lang.Object` as its `upperBound()`, where it had `null`: test `lowerBound()` first to tell `? super X` apart. See xref:concepts.adoc#language-model[Build Compatible Extensions].
* **A class outside the index is described.** In an extension, a class the index does not hold, of a dependency jar, of the JDK or of the application but not added, has its type parameters, supertypes, members and annotations, where it was a stub with none at start and frozen, and a JDK class in the processor. `superClassDeclaration()` gives the declaration of `java.lang.Object` for a class that names no other superclass, where it gave `null`: a loop that walks the superclasses up to `null` now reads `java.lang.Object` last. `superInterfacesDeclarations()` lists the interfaces outside the index too, where it left them out. `AnnotationInfo.declaration()` and an enum member's `asEnumClass()` describe a class outside the index, where they threw at start. A class nothing describes, no class file and no class of the compilation, keeps the old answers: `superClassDeclaration()` is `null`, `superInterfacesDeclarations()` leaves it out, and `declaration()` and `asEnumClass()` throw an `IllegalArgumentException`. See xref:concepts.adoc#language-model[Build Compatible Extensions].
* **A thrown type variable stays a type variable.** In an extension the container runs at start, or that the build freezes, `MethodInfo.throwsTypes()` gives a type variable for `throws E`, where it gave the class of its erasure: `asClass()` on it now throws. Test `isTypeVariable()` and read its `bounds()`, as an extension the processor runs already had to. See xref:concepts.adoc#language-model[Build Compatible Extensions].
* **A constructor is named after its class.** In an extension, a constructor's `MethodInfo.name()` is the binary name of its class, where it was `<init>`, and its `returnType()` the class type, where it was `void`. A test `"<init>".equals(method.name())` no longer finds a constructor: use `method.isConstructor()`, or `ClassInfo.constructors()`. See xref:concepts.adoc#language-model[Build Compatible Extensions].
* **An annotation shows its default values.** In an extension, `AnnotationInfo.member(name)` gives the default the annotation type declares for a member the annotation does not write, where it gave `null`; `hasMember(name)` is `true` for it, and `members()` lists it. Code that applied the default itself on `null` keeps working, and can drop that copy. Code that read `hasMember` as "written in the source" no longer can. See xref:concepts.adoc#language-model[Build Compatible Extensions].
* **An exception of `@Discovery` fails the deployment.** A build compatible extension whose `@Discovery` method throws now fails the build and the start with a `DefinitionException` that carries the exception, where the container went on without it. Fix the extension, or catch in it what it means to tolerate. See xref:internals.adoc#boot-failures[Failures are reported, not swallowed].
* **An exception of `@Enhancement` fails the deployment on every path.** An extension whose `@Enhancement` throws for a class of an unprocessed archive, or for a class a pre-processed jar replays, now fails the start and `vauban:generate`, where they went on. Fix the extension, or catch in it what it means to tolerate. See xref:internals.adoc#boot-failures[Failures are reported, not swallowed].
* **An extension parameter must be of a type its phase lists.** `@Discovery`: `ScannedClasses`, `MetaAnnotations`, `Messages`; `@Synthesis`: `SyntheticComponents`, `Messages`, `Types`; `@Validation`: `Messages`, `Types`, exactly these types, not a subtype of your own. Any other parameter type is a definition error, where the method was called with `null` for it. Remove the parameter.
* **Types show their annotations.** In an extension, `Type.annotations()`, `hasAnnotation` and `annotation` now give the annotations on a type use, where they were empty: `List<@NotNull String>` shows `@NotNull` on its type argument. Code that read a type's annotations to detect "no annotation" now sees them; annotations take no part in type equality. In the index, `ClassInfo`, `MethodInfo` and `FieldInfo` gain a last `typeAnnotations` component; their earlier constructors stay. A frozen record built by Vauban `{release-version}` stays valid for a class without type annotations; for a class with them, the start runs the extensions again until the application is built again (BUG-20261117-60).
* **A parameter without a name in the class file is `argN`.** At start and frozen, `ParameterInfo.name()` of a parameter the class file marks without naming it, an enum's or an inner class's constructor's compiled by javac 25 without `-parameters`, is `arg0`, `arg1`, ..., no longer `null`. The frozen record's checksum of a class with such a constructor changes with the names: a record an earlier Vauban wrote is refused for it, and the start runs the extensions again (BUG-20261118-31).
* **An enum's constructor loses its two synthetic parameters.** In an extension, `MethodInfo.parameters()` of an enum's constructor no longer starts with the name and the ordinal of the constant, at start and frozen: an extension that skipped two parameters there now skips the declared ones. A frozen record an earlier Vauban wrote is refused for an enum, and the start runs the extensions again (BUG-20261117-58).
* **An inner class's constructor has a receiver type.** `MethodInfo.receiverType()` of an inner member class's constructor is the class that encloses it, no longer `null`; a type variable of the enclosing class has its declared bounds in the inner class. The frozen record's checksum of an inner member class changes: a record an earlier Vauban wrote is refused for it, and the start runs the extensions again (BUG-20261118-01).
* **`ClassInfo.modifiers()` drops `synchronized` and gains a nested class's `static`.** In an extension, at start and frozen, `Modifier.isSynchronized(classInfo.modifiers())` is now `false`, and `Modifier.isStatic` is `true` for a static nested class, `isPrivate` or `isProtected` for a private or protected one. The frozen record's checksum of a nested class changes: a record an earlier Vauban wrote is refused for it, and the start runs the extensions again (BUG-20261117-37).
* **`methods()`, `fields()` and the annotations of a class include what it inherits.** In an extension, `ClassInfo.methods()` and `fields()` of a class now list the members of its superclasses and of all its superinterfaces, each with its `declaringClass()`; an annotation type's `methods()` lists `java.lang.annotation.Annotation`'s too. An extension that walked the superclasses itself finds them twice: read `declaringClass()`, or stop walking. `annotations()`, `annotation()` and `hasAnnotation()` of a class include the `@Inherited` annotations of its superclasses: a subclass of an `@ApplicationScoped` class has `@ApplicationScoped`, and a subclass of a class with `@Counted` has `@Counted`. `@Enhancement` still configures the members a class declares (BUG-20261117-42).
* **The synthetic members leave the language model.** In an extension, at start and frozen, `ClassInfo.methods()`, `fields()` and `constructors()` no longer list the members the compiler marks synthetic or bridge: a bridge method, the body of a lambda, `this$0`, `$VALUES`. An extension that counted them, or that matched a bridge for a method a superclass declares, sees what the processor saw (BUG-20261117-43).
* **A compact constructor's parameters gain their type annotations.** In an extension, at start and frozen, a parameter of a record's compact canonical constructor shows the type annotations of its record component that have a path, sit on a qualified type or on an array, as in the processor, where it showed none. The frozen record's checksum of such a record changes: a record an earlier Vauban wrote is refused for it, and the start runs the extensions again (BUG-20261118-34).
* **In the processor, an inner class's constructor gains its outer instance.** An extension the processor runs sees `MethodInfo.parameters()` of an inner member class's constructor start with the outer instance, named `arg0`, as at start and frozen; the declared parameters move up by one. A class file compiled with `-parameters` names it `this$0`, which the start shows: the processor cannot know whether the class it compiles gets `-parameters`, and keeps `arg0`, as it keeps the source's names where the start shows `argN` without the option (BUG-20261118-33).
* **A local class's constructor loses its captured values.** In an extension, at start and frozen, `MethodInfo.parameters()` of a local class's constructor no longer ends with the values the class captures; its declared parameters have their own types and annotations (BUG-20261118-32).
* **A type variable reached through a type has bounds.** In an extension, `TypeVariable.bounds()` of a type variable reached through a type, a field's, a parameter's, a return's, a supertype's argument or another variable's bound, is no longer empty: it holds `java.lang.Object` for one declared without a bound, so the same `T` equals the one `typeParameters()` gives, and a substitution keyed on the `TypeVariable` now finds it. The `T` inside `Comparable<T>` of `<T extends Comparable<T>>` has its bounds too, `Comparable<T>` again: an extension that walks the bounds of type variables recursively must stop at one it is already reading, by its name, as it must with reflection, or it does not end. Its `toString()` shows `T extends java.lang.Object` where it showed `T` (BUG-20261117-33).

== Recommended strategy

. Run the existing code on Vauban in a dedicated branch.
. Build with the Vauban toolchain (`vauban-processor` plus the `vauban-maven-plugin` `generate` goal): the compile-time deployment validation surfaces unsatisfied or ambiguous dependencies, unproxyable beans and circular dependencies at `process-classes`.
. Cover your injection graph with integration tests using `vauban-junit` (`@VaubanTest`).
. Activate the CDI 4.1 Lite TCK on the application itself via `vauban-junit`.
. Iterate on BCEs to replace portable extensions.
. If you target GraalVM `native-image`, plan for reflection metadata: class loading by name still reflects, and so do the few annotation sites nothing describes. Annotation *matching* does not — run your tests with `-Dvauban.annotations.reflection=warn` to see exactly what is left (see xref:internals.adoc#aot[AOT compatibility]).
