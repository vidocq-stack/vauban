= Concepts
:description: CDI 4.1 Lite vocabulary as Vauban materialises it — bean, scope, qualifier, producer, observer, BeanManager.

[.lead]
This page defines the dependency-injection vocabulary as Vauban materialises it. The model follows the Jakarta CDI 4.1 spec; implementation choices are described in xref:internals.adoc[Internals].

== Bean

A _bean_ is a class managed by the container: its lifecycle, its dependency resolution and its scope are controlled by Vauban.

Three conditions are enough for a class to become a Vauban bean:

. The class is annotated with a scope (`@ApplicationScoped`, `@Singleton`, `@Dependent`, `@RequestScoped`, or a scope of your own) or a stereotype.The annotation processor recognises any annotation meta-annotated `@Stereotype`, `@NormalScope` or `@Scope`, declared in the same compilation or in a library; it used to index only the classes carrying a built-in scope, `@Produces` or `@Interceptor`, so a class marked only with an application stereotype was no bean (vauban#132).
. The class is visible from the `module-info.java` (`exports` or same module).
. The class shows up in the bean index written at compile time by the annotation processor, or by the Maven plugin for archives it did not compile.

At compile time, each package receives a generated `_VaubanComponents` provider, which instantiates and injects its beans, and each bean, when it needs them:

* a `_ClientProxy` — only for normal scopes; intercepts calls and delegates to the active context;
* a `$$Intercepted` subclass — only for a bean with interceptor bindings; runs its interceptor chains.

== Scope

A _scope_ defines an instance's lifetime and the context that holds it.

== Qualifier

A _qualifier_ is a runtime annotation that discriminates beans of the same type. The _Default qualifier_ is implicit. CDI ships `@Default`, `@Any`, `@Named`; Vauban supports all custom qualifiers, including those with `@Nonbinding` members.

== Producer

A `@Produces` method or field produces a bean whose instantiation is not controlled by the container but by user code. The associated _disposer_ (`@Disposes`) runs on destruction. No dedicated class is generated per producer: the container builds the producer bean at runtime from the declaring bean (created through the provider of its package) and invokes the producer and disposer through the module's generated `_VaubanComponents` provider, falling back to reflection only when no provider arm exists.

== Observer

An _observer_ is a `@Observes` or `@ObservesAsync` method that reacts to an application event. Async observers are dispatched on virtual threads. Observer resolution is static: the `EventDispatcher` consults a table built at compile time.

== Interceptor

An _interceptor_ wraps a method invocation (`@AroundInvoke`) or constructor (`@AroundConstruct`). Interceptor chains are resolved at compile time and run by the bean's `$$Intercepted` subclass.

== BeanManager

The `BeanManager` is CDI's SPI façade. Vauban exposes it as `VaubanBeanManager`, read-only for application code. It allows:

* programmatic bean resolution (`getBeans(Type, Qualifier...)`);
* observer resolution;
* access to active contexts.

The historical mutable methods (`addBean`, `addObserverMethod`) are unavailable: everything is frozen at build time.

The user never touches the generated classes. They call `VaubanContainer.builder().build()`, select a root bean, and the container does the rest.

[#inject-constructor]
The injection points of an `@Inject` constructor are typed from that constructor, even when the class
declares another constructor with the same number of parameters: an `Instance<T>` parameter stays an `Instance<T>`,
which the container never validates as ambiguous or unsatisfied.

== Build Compatible Extensions

CDI 4.1 introduces Build Compatible Extensions (BCEs): `@Discovery`, `@Enhancement`, `@Registration`, `@Synthesis` and `@Validation` hooks. Vauban runs them in the annotation processor at build time and records the result.Each phase runs for every extension before the next one starts, so an extension's `@Registration` sees the beans as every `@Enhancement` left them, including the classes an enhancement made beans (vauban#131).The recorded result keeps the member values of the annotations an `@Enhancement` adds, so an added `@Named("x")` or a qualifier member reaches the container (vauban#135). At boot, the container runs them only for archives the build did not process, and replays the enhancements the recorded patch does not cover; a build that sees the whole deployment goes further and spares the start the extensions altogether (<<frozen-extensions>>). The tests under `vauban-core/src/test/java/io/vidocq/vauban/core/extensions/` exercise each hook — `BceEnhancementTest`, `BceRegistrationSynthesisTest` and `BceRuntimeReplayTest` among them.

[[classes-outside-the-index]]An extension that follows a class from a type or an annotation value — `@JsonbTypeAdapter(AmountAdapter.class)`, say, read through `annotation.value().asType().asClass().declaration()` — sees that class's fields, methods and constructors at build time too, even when it is neither a bean nor carries an annotation an extension asked for: the processor describes it from the compilation, as the container does at boot (VAU-BCE-008). Describing it does not make it a bean. The JDK's classes stay names without members, as at boot.

[[broken-extension-entry]]The processor finds the extensions through `META-INF/services/jakarta.enterprise.inject.build.compatible.spi.BuildCompatibleExtension` on its processor path. A provider listed there that cannot be loaded or instantiated is skipped with a compiler warning naming the service file and the provider, and the other extensions still run; it used to fail the compilation with a `ServiceConfigurationError` (vauban#199). `vauban:generate` does the same for the `@Enhancement` phase it runs (vauban#189).

An enhancement that adds `@Inject` to a field or initializer creates its injection points,
including every initializer parameter; constructor and initializer qualifier changes retain their
member values and identify the exact overload (vauban#139).An enhancement that adds
`@Inject` to a constructor makes it the bean constructor, as CDI requires: the container creates the
bean through it rather than through the no-arg constructor, and reports its parameters as injection
points (vauban#187). This also applies to a class that gains
its scope through enhancement. The frozen build-time patch records class and member additions,
so boot does not need to instantiate the extension again to restore them.
Direct generated field writes and method calls remain the first access path. For a managed class
whose package provider grants its module lookup, non-public enhanced fields and private initializers
need no `opens`; a declaring class without that grant still needs a supplied lookup or qualified opens.
The frozen patch records annotation additions, not removals.
The patch of an archive applies to the classes a deployment holds: a container built from some of the classes of a
processed archive (`addBeanClass`, `scanLocal`, `scanPackage`) leaves out the entries of the others. Member entries of
a class outside the deployment used to fail the boot with _Enhanced class is missing from the index_ (BUG-20261111-02).

The beans an extension synthesises in the processor travel in `META-INF/vauban-synthetic-metadata.properties`, never in `META-INF/vauban-beans.list`: a synthetic bean has no class of its own for the container to discover.The bean list used to name them too, so an application whose extension synthesised a bean of a JDK type (Ravel's, typed `java.lang.String`) failed to boot with a `NullPointerException` (ravel#21).A bean type given as a language-model type — `addBean(...).type(types.ofClass(info))`, for a class the compilation is still producing — is written into that metadata by name, like a `Class` type, and loaded at run time. Only the `Class` types used to be written, so the bean was typed `Object` alone at run time and its injection points were unsatisfied. A *parameterized* language-model type, `Optional<String>` say, is written in the notation of the observed types described below and keeps its arguments at boot; it used not to be written at all, which went unnoticed as long as the extension ran again at each start and declared the bean anew (BUG-20261008-01, VAU-PERF-005).

The qualifiers of a synthetic bean or observer are written into that metadata with their member values, so `@Channel("alpha")` and `@Channel("beta")` stay two qualifiers at boot. Only the qualifier's type name used to be written when the processor ran the extension: the bean matched no injection point that names a member value, and the deployment failed with _Unsatisfied dependency_ (BUG-20261111-01). An archive built by an earlier version, which names the types only, still reads.

A synthetic observer can observe any type the language model expresses: a parameterized type with a wildcard argument (`List<? extends Number>`), a generic array (`List<String>[]`, `T[]`) or an array of a class, besides a class and a parameterized type. `addObserver` used to refuse these in `@Synthesis` with _Unsupported type for synthetic observer_. They are observed whether the container or the processor runs the extension (VAU-OBS-003, vauban#188).When the processor runs it, the metadata records the observed type in a notation the boot reads back: `java.util.List<? extends java.lang.Number>`, `java.lang.String[]`, `(N extends java.lang.Number)[]` for a type variable with its bounds. An observer of a parameterized type such as `List<String>` used to be recorded by a name the boot could not load, and was dropped at boot without a word; a value the boot cannot read now fails the deployment (VAU-OBS-005, vauban#206).The observed type may be a class the compilation is still producing, alone or as a type argument (`addObserver(types.ofClass(info))` with the `ClassInfo` from `@Registration`): the processor records it by name and the boot loads it. It used to fail the build with _Cannot resolve type_ (VAU-APT-003, vauban#210).

Every value `withParam` accepts reaches the creator or the observer when the extension ran in the processor: primitive, `String`, `Class`, `Enum` and annotation arrays, a `ClassInfo` (looked up as a `Class`), an `Annotation` or `AnnotationInfo` (looked up as the annotation, every member kept) and an `InvokerInfo`. Arrays, annotations and invokers used to be dropped without a word, and `Class` and `Enum` params were lost at boot, so the creator read `null`; a synthetic observer got none of its params. A param the build cannot record now fails the build, naming the bean and the param, and a param naming a class the boot cannot load fails the deployment (vauban#130, BUG-20261008-02).

The language model an extension reads comes from the Vauban index, which the processor builds from the source and the container from the class files. `ClassInfo.typeParameters()` gives the type parameters a class declares, each with its bounds (`java.lang.Object` when none is declared); it used to return an empty list (VAU-BCE-007, vauban#207). A class outside the index, such as a JDK type reached through `ClassType.declaration()`, has no type parameters there.

[#extension-phase]
=== Build time or container start

CDI Lite lets an implementation run an extension at either moment and does not tell the extension which. Most extensions do the same work both times. One that checks the deployment's environment — a configuration value, a resource the application will open — would find the build machine's in the processor. `io.vidocq.vauban.api.ExtensionPhase.isBuildTime()` tells it: `true` while the annotation processor or the Maven plugin runs it, `false` when the container does. Such an extension leaves the check to the container start.

The answer belongs to the calling thread, for the duration of the call that opened the phase (`ExtensionPhase.atBuildTime(...)`, a `ScopedValue` binding). A build tool that runs extensions itself opens it the same way.

Asking has a cost once the build freezes the extensions (<<frozen-extensions>>): an extension that asked left work for the start, so the container runs it again at each start, where every other extension is loaded from the build's record. <<writing-a-frozen-extension>> says how to keep an extension out of that case.

[#frozen-extensions]
=== Extensions frozen at build [.tag-new]#NEW#

The annotation processor runs the extensions on one module, while it compiles. It cannot answer for the whole deployment: the classes it compiles are not loadable yet, the dependency archives hold beans other extensions act on, and an extension of another archive may not be on the processor path at all. So, until now, the container ran every extension again at each start as soon as one bean archive carried no `vauban-bce-processed` marker, which is every application assembled from several jars. On an application with ten extensions that cycle took about 60 ms of a 430 ms start (BENCH-20261113-01).

A build step that runs after compilation and sees the deployment as the start will see it — `vauban:generate` with `freezeExtensions`, or the build of a runtime that embeds Vauban — closes the gap. It runs the extension cycle once more, the way the container start does, at build time (`ExtensionPhase.isBuildTime()` answers `true`), and writes what the extensions did in the application's output:

* `META-INF/vauban-frozen-extensions.properties`: a fingerprint of the deployment, the extensions that ran, those that run again at start, and what `@Discovery` registered — qualifiers, interceptor bindings, stereotypes, non-binding members, contexts, scanned classes;
* `META-INF/vauban-frozen-enhancements.properties`: the annotations `@Enhancement` added, in the format of the frozen patch;
* `META-INF/vauban-frozen-synthetic.properties`: the synthetic beans and observers, in the format of the synthetic metadata.

At start, the container computes the fingerprint of its deployment: the bean classes by name and by what the extensions see of them, the extensions among them by their code as well, and the builder's discovery settings. With a record of that fingerprint on its path it loads the record instead of running the extensions; `VaubanContainer.extensionsAtStart()` says which it did. Anything else runs the extensions as before, and the record is left alone: no record, a class added or removed since, a change an extension could see, a change to an extension, an archive added to the path (a development console, a test class path), two records. The files the processor wrote in each archive are read as before in both cases.

What an extension sees of a bean class is what the language model shows it: the name, the supertypes, the modifiers, the fields and methods with their types, and the annotations. The body of a bean's method is not part of it, so changing one keeps the record. Neither is the debug information of a class file: `jlink --strip-debug` removes the source file, the line numbers, the local variables and the parameter names from the classes of an image, and that image keeps the record of its build. An extension counts by its code too, the constant pool and the bytecode of its methods: what it does is in its method bodies. Code an extension calls in another class counts only by what the language model shows of that class, when it is a bean class at all; build the application again after changing such a class.

No brick jar is copied or marked: the record is the application's, one per deployment.

The build writes no record, removes a stale one and says why, when the result cannot be frozen faithfully:

* an extension failed or reported an error: the start reports it, in the environment it belongs to;
* an `@Enhancement` removed annotations, which a record of additions cannot say;
* a synthetic bean or observer holds a parameter the metadata cannot express.

Two things keep a record from saying too much. An extension that asked `ExtensionPhase.isBuildTime()` during the build is recorded as running again at each start, and what it did is left out of the record; `startExtensions` names more of them, for an extension that depends on its start environment without asking. And a bean the embedding runtime adds itself, with `VaubanContainerBuilder.addHostBean(type, factory)`, stays out of the fingerprint: such a bean may depend on the start configuration (a holder for a connection pool that is configured or not), so it must not invalidate the record; in return, the frozen extensions never saw it. A class the deployment holds anyway, one its beans list names, stays in the fingerprint even when the runtime also adds it this way: the build counted it.

[#writing-a-frozen-extension]
=== Writing an extension the build can freeze [.tag-new]#NEW#

An extension is frozen when its work depends on the classes of the deployment and on nothing else. Four rules get it there; each of them also makes the extension behave the same on a container that runs extensions at build only.

. *Compute from the deployment only.* What a phase reads — classes, annotations, the beans `@Registration` shows — is the same on the build machine and where the application starts. A configuration value, an environment variable, a file outside the application, a network resource is not: keep them out of the phases.
. *Check the start environment in an observer of `Startup`, not in a phase.* A required configuration value, a key that must parse: collect at build what must be checked, hand it to the start as the parameters of a synthetic observer (`SyntheticComponents.addObserver(Startup.class).withParam(…).observeWith(…)`) or of a synthetic bean an ordinary observer injects, and do the check when `Startup` fires. To refuse the deployment, throw a `DeploymentException`: the container start fails with that very exception (xref:usage.adoc#lifecycle-observer-failures[When a lifecycle observer throws]). Give the observer an early `@Priority` so that it runs before the application's own `Startup` observers.
. *Add, never remove.* `ClassConfig.addAnnotation` freezes; `removeAnnotation` and `removeAllAnnotations` do not, and send the whole deployment back to running its extensions at start. To replace an annotation's effect, add the one that wins.
. *Carry data in parameters the metadata can write.* Primitives, `String`, `Class`, enums, annotations, `ClassInfo`, `AnnotationInfo`, `InvokerInfo` and their arrays; state the extension keeps in a field is gone at start, since no extension instance exists there.

When a phase cannot avoid the start environment, ask `ExtensionPhase.isBuildTime()` and skip that part at build time: the container then runs the extension again at each start, and only it. That is the slow path. It is worth moving the part that asks into a class of its own, so that the rest of the extension stays frozen.

Test both ways: a container that runs the extension, and one built from `freezeExtensions` output, where the extension must not be instantiated (`extensionsAtStart().ranAtStart()` is empty) and the application behaves the same.

[#synthetic-interface-proxies]
=== Client proxies of synthetic beans [.tag-new]#NEW#

A bean of a normal scope is injected through a client proxy, which the processor generates for the beans it sees: a class, or a producer, an interface-typed one included (a class that `implements` the interface, in the producer's package). A synthetic bean has no class the processor sees. The container used to proxy one of an interface type with a `java.lang.reflect.Proxy` at boot, every call going through reflection, with the boot warning of xref:internals.adoc#aot[AOT compatibility], whose advice to add `vauban-processor` did not apply (BUG-20261113-19).

The extension that registers such a bean lists its interface in `@io.vidocq.vauban.api.ClientProxies`, on any class of a module compiled with `vauban-processor`:

[source,java]
----
@ClientProxies({EntityManager.class, EntityManagerFactory.class})
public class PersistenceExtension implements BuildCompatibleExtension {

    @Synthesis
    public void synthesize(SyntheticComponents components) {
        components.addBean(EntityManagerFactory.class).type(EntityManagerFactory.class)
                .scope(ApplicationScoped.class).createWith(FactoryCreator.class);
    }
}
----

The processor generates a class that `implements` each listed interface, in the package of the annotated class, forwarding every method, abstract or `default`, to the contextual instance. The module's `_VaubanComponents` provider creates it, and the processor writes that provider even for a module with no bean of its own; the module declares it, `provides io.vidocq.vauban.api.VaubanComponentProvider with <package>._VaubanComponents;`. The container looks the proxy up by its interface, so it serves every synthetic bean of that interface, whichever extension registers it. A listed type that is not a public interface fails the compilation.

A brick that stays container-neutral, without a dependency on Vauban, leaves the list to the module that assembles it with Vauban, such as its Vidocq runtime extension. The boot warning names the proxy of a synthetic bean apart, _interface client proxy (java.lang.reflect.Proxy) of a synthetic bean_, with this advice.

== Differences from CDI Full

Vauban implements the _Lite_ profile. The following are absent:

* runtime portable extensions (`Extension`, `BeforeBeanDiscovery`, etc.) — replaced by BCEs;
* `@Specializes`;
* `@ConversationScoped`;
* passivation (`PassivationCapable`);
* EL (Expression Language) wired into managed beans.

See xref:reference.adoc#lite-vs-full[the comparison table].
