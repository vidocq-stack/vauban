= What's new
:description: Everything that changed in this component since the {release-version} release.

[.lead]
New in the `{project-version}` development line — everything listed here landed **after the {release-version} release** and is not part of it. Every entry links to the section that documents it, and those sections carry the [.tag-new]#NEW# badge. Each brick of the suite keeps its own page of this kind; xref:home::whats-new.adoc[the ecosystem index] gathers them. When the next release train ships, this page is frozen with it and restarts empty on the dev line.

* **An exception reported through `Messages` is the cause of the deployment problem.** An extension that reports `Messages.error(Exception)` fails the start with a `DeploymentException` whose cause is that exception, the others it reported suppressed, in every phase, `@Discovery` included; the message alone was kept (BUG-20261118-59). See xref:internals.adoc#boot-failures[Failures are reported, not swallowed].
* **An exception of `@Enhancement`, `@Registration` or `@Synthesis` is a definition error.** A method of one of these phases that throws now fails the start, the start after a freeze and, for `@Enhancement`, `vauban:generate` with a `DefinitionException` whose cause is the exception, as one of `@Discovery` does; the build fails as before. They failed with a `DeploymentException`, and only `@Enhancement` carried the exception. A `DeploymentException` the method throws, as `InvokerFactory.createInvoker` does, stays a deployment problem, and so does an exception of `@Validation`, which now carries the exception as its cause too (BUG-20261118-57). See xref:migration.adoc#upgrading[Upgrading] and xref:internals.adoc#boot-failures[Failures are reported, not swallowed].
* **An invoker's lookup of `Outer<String>.Plain` keeps the owner.** With producers of `Outer<String>.Plain` and `Outer<Long>.Plain`, an invoker that looks up an `Outer<String>.Plain` argument was refused as ambiguous in the processor, at start and frozen; it now resolves the `Outer<String>` one, as reflection does (xref:concepts.adoc#classes-outside-the-index[Concepts], BUG-20261118-56).
* **An invoker's lookup reads the qualifiers a subclass's config gave an inherited parameter.** `@Enhancement` adds `@Named("x")` to the parameter of `Base.pick(String)` through `Service`'s `ClassConfig`; an invoker of `pick` for the bean `Service` that looks the argument up now asks for `@Named("x") String`, as the container injects such a parameter. It asked for the parameter as `Base` declares it, in the processor, at start and frozen (xref:concepts.adoc#language-model[Concepts], BUG-20261118-55).
* **`@Registration` sees the injection points a bean inherits.** `BeanInfo.injectionPoints()` gave the injection points the bean class declares only: not the `@Inject` fields and initializer parameters of its superclasses, in the processor, at start and frozen. It gives them now, with the qualifiers the `@Enhancement` configs of that class left, and `InjectionPointInfo.declaration()` of a parameter is the `ParameterInfo`, where it was the bean class (xref:concepts.adoc#language-model[Concepts], BUG-20261118-50).
* **An invoker's looked-up argument keeps the owner of its type.** An invoker with `withArgumentLookup` on a parameter `Outer<String>.Inner<Integer>` was refused as ambiguous when a bean of `Outer<Long>.Inner<Integer>` existed too, in the processor, at start and frozen: Vauban read the parameter's type from the language model, which has no owner, and an ownerless type matched both (xref:concepts.adoc#classes-outside-the-index[Concepts], BUG-20261118-49).
* **An inherited observer reads the owner of its parameter's type as the bean class gives it.** A superclass observer `on(@Observes Pung, Outer<X>.Inner<String>)`, inherited by `extends Base<String>`, needs an `Outer<String>.Inner<String>`: the start kept `Outer<X>`, found no bean and refused the deployment, which the build accepted. A parameter whose owner the bean class leaves a type variable is left to the start at build, as one whose type arguments do (xref:concepts.adoc#classes-outside-the-index[Concepts], BUG-20261118-54).
* **The CDI language model TCK runs with the core TCK.** Under `-Ptck`, `vauban-tck-runner` runs the `LangModelVerifier` of `cdi-tck-lang-model`, which nothing ran before, at start, in the annotation processor and in a deployment frozen at build, with the type annotation checks on: one test per step of the verifier, a step that fails for a known bug skipped and naming it (xref:tck.adoc#language-model-tck[TCK: language model]).
* **`@Registration` gets the built-in beans, and no class that is no bean.** A `@Registration` method with a `BeanInfo` parameter is now also called for the container's built-in beans whose bean types contain one of its `types` (`BeanManager`, `Instance`, `Event`, `InjectionPoint`, `Bean`, `Interceptor`, `RequestContextController`, the `@Intercepted Bean`), in the processor, at start and frozen. `InvokerFactory.createInvoker` refuses a bean that is no managed bean, and every other invoker it may not build, with a `DeploymentException`, as Weld does. When no bean had one of its types, it was called at start for the classes of the deployment that had one, beans or not; it no longer is (BUG-20261117-06).
* **A bean no longer inherits the static observer methods of its superclass.** CDI 4.1 lets a bean inherit the non-static observer methods of its superclasses only. A bean got the static ones too, in the processor, at start and frozen; when the superclass was a bean as well, its static observer was registered again for each bean below it, and an event reached it as many times (BUG-20261118-51).
* **The phases after `@Enhancement` no longer see the annotations it removed.** An annotation `removeAnnotation` or `removeAllAnnotations` took off a class, a field, a method or a parameter was still on it for `@Registration`, `@Synthesis` and `@Validation`, in the processor and at start. They now read the classes as `@Enhancement` left them, removals included. A build still refuses to freeze a removal (BUG-20261118-45).
* **`@Registration` sees the annotations `@Enhancement` added to members.** An annotation an extension added to a field, a method or a parameter in `@Enhancement` was missing from the fields, methods, parameters and producer member of the `BeanInfo` a `@Registration` method reads, in the processor, at start and frozen. The phases after `@Enhancement` now read every class as that phase left it, members included (BUG-20261118-42).
* **An `ObserverInfo` gives the method a bean inherits.** The `ObserverInfo` of an observer method a bean inherits from its superclass gave no `observerMethod()` and no `eventParameter()` at start and frozen, and the processor gave no such observer to `@Registration`. It now gives the method of the superclass, in the three places, with its event type after the substitution of the type arguments the bean class gives; its `declaringClass()` and `bean()` stay the bean class (BUG-20261118-44).
* **An `ObserverInfo` tells apart two overloads that observe one event type.** The `ObserverInfo` of `hear(BeanManager, @Observes Long)` and of `hear(@Observes Long)` both gave the first overload. An observer now carries the erased types of its method's parameters, and gives its own method and event parameter, in the three places (BUG-20261118-41).
* **`@Registration` gives a `@Typed` bean for its types only.** At start and frozen, a `@Registration` method was given a `@Typed(Talker.class)` bean when it asked for a supertype of `Talker`, which the bean does not have. A bean type now matches an expected type of the same name, in the three places (BUG-20261118-43).
* **In the processor, `@Registration` sees the annotations `@Enhancement` added.** The `ClassInfo` a `@Registration`, `@Synthesis` or `@Validation` method read in the processor showed a class as it was compiled, without the annotations an `@Enhancement` method added; at start and frozen it showed them. The phases after `@Enhancement` now read an index with those annotations in the three places (BUG-20261117-10).
* **An `@Enhancement` method is called once for each type.** At start, and in the build that freezes the extensions, the container called an `@Enhancement` method twice for each type it matches: once in the pass that enhances the classes no processor saw, before it discovers the beans, and once more with the other phases, each time on an instance of its own. It now runs that pass once, on the instance the extension's `@Discovery` ran on, over the classes no processor saw and those `@Discovery` added, and calls no `@Enhancement` method again with the other phases; the processor already called it once (BUG-20261117-08).
* **`@Registration` gets the producers of primitive and array types.** A `@Registration(types = int.class)` or `Integer.class` method with a `BeanInfo` parameter was not called for a producer of `int`, nor a `String[].class` one for a producer of `String[]`, in the processor, at start and frozen: a bean type was matched by loading the class it names, and a primitive or an array names none. The bean types of such a producer are its type and `Object` (CDI 4.1, 2.2.1): a producer of `int` is now matched by `int.class` and `Integer.class`, one of `String[]` by `String[].class`, and neither by `Number` nor `Serializable` (BUG-20261117-11).
* **An `ObserverInfo` gives its method, event parameter, bean and qualifiers.** In a `@Registration` method, an `ObserverInfo` answered `null` from `observerMethod()`, `eventParameter()` and `bean()`, and no `qualifiers()`, in the processor, at start and frozen: an extension that read them threw `NullPointerException` and failed the deployment. They now give the method of the declaring class with the observer's name whose `@Observes` or `@ObservesAsync` parameter has the observed event type, an overload of another event type told apart; that parameter; the managed bean that declares it; and the qualifiers the parameter declares (BUG-20261117-09).
* **An `InterceptorInfo` gives the bean types, qualifiers and injection points of its interceptor.** A `@Registration` method got an `InterceptorInfo`, or a `BeanInfo` of an interceptor, with no type, no qualifier and no injection point, in the processor, at start and frozen. CDI 4.1 describes an interceptor as a bean: it now reads its class as the managed bean it would be, so an extension that synthesizes a bean for each injection point it sees, as Ravel's does for `@ConfigProperty` and Cervantes' for `@Claim`, sees those of an interceptor too (BUG-20261117-04).
* **A `BeanInfo` gives its producer member, its disposer and its stereotypes.** In a `@Registration` method, the `BeanInfo` of a producer answered `null` from `producerMethod()` and `producerField()`, and every `BeanInfo` `null` from `disposer()` and no `stereotypes()`, in the processor, at start and frozen: an extension that read the producer's member threw `NullPointerException` and failed the deployment. They now give the method or the field, found by the name and, for an overloaded method, the erased parameter types its bean id carries; the disposer method of the declaring class whose `@Disposes` parameter has one of the bean's types and its qualifiers; and the stereotypes the class or the member declares, with their scope, `@Alternative`, `@Priority`, `@Named` and interceptor bindings (BUG-20261117-13).
* **An invoker the build describes calls its method through a generated class.** For an invoker of a bean whose class it compiles, the annotation processor, and `vauban:generate` when it freezes the extensions, write a class next to the bean class that calls the method by name; the start loads it and resolves no `java.lang.reflect.Method`. The start used to find the method with `getDeclaredMethod` and call it through `unreflect` or `Method.invoke`. An invoker built at start stays reflective (BUG-20261118-37).
* **An interceptor instance for each intercepted instance.** Two intercepted `@Dependent` beans created with one creational context, for example by a bean constructor that injects both, shared their interceptor instances, and the second's `@Intercepted Bean` named the first. Each intercepted instance now has a creational context of its own (BUG-20261118-36).
* **The bean metadata beans of CDI Lite.** A bean may inject its own `Bean`, an interceptor its own `Interceptor` and the `@Intercepted Bean` of the bean it intercepts (CDI 4.1, 5.5.8): the container provided none, and the creation of such a bean or interceptor failed with "No bean found for type" (BUG-20261117-47).
* **An interceptor may inject `@Intercepted Bean<?>` and its own `Interceptor`.** The deployment refused `@Intercepted Bean<?>` and `Bean<? extends Object>`, read from the index as a bounded wildcard, and the annotation processor, which did not see the interceptor it compiles, refused `Interceptor<Itself>` too (BUG-20261117-41).
* **An extension that runs at start may look up the synthetic beans of the others.** The start checked an invoker's argument lookups before it registered the synthetic beans of the extensions frozen at build and of the archives the annotation processor processed, and refused a lookup only one of them satisfies. It now checks them among every bean of the deployment (BUG-20261117-45).
* **An invoker may look up every built-in bean the call serves.** The start refused an argument lookup of the `BeanContainer`, a `Provider`, the `RequestContextController` or the `InjectionPoint` as unsatisfied, though the call gives them: it left only `Instance`, `Event` and the `BeanManager` to the container. The lookup check now reads the deployment validation's list of built-in beans (BUG-20261117-44).
* **An invoker's instance lookup finds a target bean that has a qualifier.** An invoker built `withInstanceLookup()` selected its bean class with `@Default`: the call threw `UnsatisfiedResolutionException` for `@Fast FastWorker`, and for a bean whose `@Typed` leaves its class out. It now asks for a contextual reference for the target bean, of the bean type that declares the method (CDI 4.1, "Configuring lookups"; BUG-20261117-38).
* **An extension builds an invoker of a bean the build compiles.** `InvokerFactory.createInvoker` loaded the bean class to find the method, and the annotation processor failed the compilation with `Cannot load bean class: app.Worker` for a class it compiles. The build now describes the method by names, from the language model, records the invoker so, and the start finds the method back; the build checks the argument lookups of such an invoker as of any other (BUG-20261117-48).
* **A class an extension adds through `ScannedClasses` is checked like a bean class.** The start skipped the class-level definition rules of a class only an extension's `@Discovery` added: `@Dependent ScannedSetter<T>` with `@Inject void set(T value)` started. It now fails with a `DefinitionException` (BUG-20261118-12).
* **The build resolves the parameters of an inherited or a static observer.** A bean that inherits `void on(@Observes Pung pung, Tool tool)`, or declares it `static`, with two beans of type `Tool`, failed the start only: the build resolved the parameters of the instance observers a bean class declares. It now fails the build as well, and a parameter of a type no bean of the compilation declares leaves the start to decide, with a warning (BUG-20261118-11).
* **A scope an extension adds to a generic class is checked.** A generic managed bean must be `@Dependent` (CDI 4.1, 3.1). The check read the annotations the class declares: `Resource<T>`, to which an `@Enhancement` added `@RequestScoped`, started, and its bean was request-scoped. The start now throws a `DefinitionException`, `Managed bean ...Resource has type parameters and is not @Dependent: @jakarta.enterprise.context.RequestScoped`, as Weld does (WELD-000071), and the build warns of it; the message of a scope the class declares names that scope too. Cassini's `CassiniScopeExtension` gives a generic `@Path` class `@Dependent` since CASSINI-065 (BUG-20261117-35).
* **An `@Inject` field of a type variable is a definition error.** `@Inject T gadget` in the bean `GadgetField<T>` is an injection point of a type variable (CDI 4.1, 5.2.3): the build now warns, `Injection point has type variable type T: ...GadgetField.gadget`, and the start throws a `DefinitionException` with it, where the build failed and the start threw a `DeploymentException`, the field looked up by its erasure as an ambiguous or unsatisfied dependency. A field inherited from an abstract or vetoed class counts when the bean class leaves it a type variable, `GenericFieldOfVetoed<T> extends VetoedGadgetField<T>`, and not when it gives it a class, `GadgetFieldOfVetoed extends VetoedGadgetField<Gadget>`, as the CDI TCK's `inheritance.generics` has it. The build also validates a bean class whose superclass it did not index, such as a vetoed one (BUG-20261117-29). A concrete class without a bean-defining annotation is no bean: its field is checked as its bean subclass gives it.
* **A non-contextual injection point no longer falls back on its erased class.** A class that is no bean, injected through `BeanManager.getInjectionTargetFactory(...).createInjectionTarget(null).inject(...)` or created by `Unmanaged`, with `@Inject Foo<Integer> foo` and only a producer of a raw `Foo`, got that `Foo`: when `getBeans` found no bean, the injection looked the erased class up, which the raw producer satisfies. It now throws an `UnsatisfiedResolutionException`, `No bean found for type: ...Foo<java.lang.Integer>`, as the start refuses the same injection point on a bean (CDI 4.1, 5.2.4). An initializer's call wraps it in a `ContainerOperationException`, as any failure of the call. An injection point of a class keeps its lookup (BUG-20261117-28). Nor does a qualified one, or one of a type variable a subclass gives a class: `@Inject @Red Knob` got the `@Default Knob`, and a field of `Missing` any bean of `Object`; each throws `UnsatisfiedResolutionException` now.
* **The start checks the parameters of an inherited observer.** A bean that inherits `void on(@Observes Pung pung, Holder<Integer> holder)` from an abstract or vetoed class, with no bean of `Holder<Integer>`, now fails the start with a `DeploymentException`, `Observer method InheritedIntegerHolderListener.on(): unsatisfied dependency for parameter arg1 of type ...Holder<java.lang.Integer>`, extensions run or frozen: the start read the observers the bean class declares only, and the call failed at the first event. The parameters are read as the bean class gives its superclasses' type variables, `Holder<X>` as `Holder<String>` for `TextHolderListener extends HolderListener<String>`, as the call already read them. A bean that passes its own type variable on, `GenericListenerOfVetoed<T> extends VetoedTypeVariableListener<T>`, leaves the inherited parameter a type variable: a `DefinitionException`, `Injection point has type variable type T: ...GenericListenerOfVetoed.on observer param 1` (CDI 4.1, 5.2.3) (BUG-20261117-26).
* **An initializer's parameter of a type variable is checked on a class that may be a bean.** `@Inject void set(T gadget)` in `GadgetSetter<T extends Gadget>`, a bean, is a definition error (CDI 4.1, 5.2.3): the build now warns of it, and the start names it `Injection point has type variable type T: ...GadgetSetter.set initializer param 0`, or `... constructor param 0` for a bean constructor, where it said `Injection point has type variable type: ...GadgetSetter.set`. The same initializer in an abstract or `@Vetoed` class, or in a class of a vetoed package, is no longer refused: a bean that inherits it, `GadgetSetterOfAbstract extends AbstractGadgetSetter<Gadget>`, gets a `Gadget`, as an inherited observer already did. The start checked the initializers of every class of the index, a bean or not, and refused the deployment. A class is a bean as bean discovery decides: a concrete class without a bean-defining annotation is none, so the initializer it declares is checked as its bean subclass gives it, and a class an extension makes a bean is checked once the extensions ran. A bean that inherits an initializer and leaves its parameter a type variable of its own, `GenericSetterOfVetoed<T> extends VetoedSetter<T>`, is now refused at start and warned of at build, where it started and failed at the first lookup (BUG-20261117-30).
* **A client proxy generated as bytecode forwards a bridge to a superclass method.** A normal-scoped bean that inherits `String tag(String)` from a superclass and implements `Tagged<String>`, whose `tag(T)` that method implements, ran a call typed by `Tagged` on the proxy instance. javac implements the interface method through a bridge `tag(Object)` that calls the superclass method directly, past the proxy's override. The proxies the container and `vauban:generate` generate, and the processor's bytecode proxies, now forward that bridge too; the processor's source proxies were right (BUG-20261118-17). A bean bound to an interceptor still lets such a call past the interceptor on the run-time path (BUG-20261118-18).
* **A disposer that throws is logged.** The container still destroys the produced instance, as CDI 4.1 §6.1 asks, and now logs a WARNING, `Disposer method <class>.<method> failed; the produced instance is destroyed all the same`, with the exception, where it was silent (BUG-20261118-19).
* **A bean that inherits a final method is unproxyable.** `@ApplicationScoped class Service extends Base`, where `Base` declares `public final String tag()` and is no bean, or comes from a library, started and resolved, and a call of `tag()` ran on the client proxy itself. Every proxyability check now walks the superclasses, a package-private `final` method of another package included, at start and in the annotation processor. The type the bean is requested as decides: injected or looked up as its class, such a bean fails the deployment or throws `UnproxyableResolutionException`; injected or looked up as an interface it implements, it works (CDI 4.1 §3.10, BUG-20261118-19). See xref:migration.adoc#upgrading[Migration].
* **A bean whose class has a final method is proxied through its interfaces.** Looked up or injected as an interface whose method a `final` method of the bean class implements, the call ran on the client proxy, not on the bean. The client proxy of such a bean now extends the nearest class above the `final` method that has none, often `Object`, and implements the bean's interfaces, at run time, in `vauban:generate` and in the annotation processor alike (BUG-20261118-20). Since the proxy may not extend the bean class, `io.vidocq.vauban.api.ClientProxyClass.beanClassOf(proxy.getClass())` tells the class a client proxy stands for, so code that reads a bean's annotations behind its proxy finds them. See xref:migration.adoc#upgrading[Migration].
* **A final normal-scoped bean class works through its interfaces.** It was refused whatever type it was requested as, and the annotation processor wrote a client proxy that extends it, which does not compile. CDI 4.1 §3.10 refuses it only as its own class: injected or looked up as an interface it implements, it now gets the client proxy of BUG-20261118-20, which extends `Object` and implements its interfaces (BUG-20261118-21).
* **A normal-scoped producer of a parameterized type gets the proxy of its type.** `@Produces @RequestScoped Supplier<String>`, `Box<Integer>`, or `@Typed(Repo.class) Box<String>`: every bean type of such a producer is parameterized, and the container skipped them all. It proxied the class that declares the producer, or a class or interface above the produced type with no type arguments (`RandomAccess` for `ArrayList<String>`), which the injection point could not take; the annotation processor and `vauban:generate` wrote no proxy. The three now read the type raw: the proxy of `Supplier`, of `Box`, of `Repo` (BUG-20261117-18). A producer of `ArrayList<String>` is now refused with a message that names the remedy: a Vauban limitation that departs from Weld, which deploys it (BUG-20261118-24).
* **An intercepted subclass generated as bytecode declares the bridges javac would.** On the same shape, a call typed by `Tagged` to a bean bound to an interceptor reached the instance past the interceptor: the bean's bridge `tag(Object)` called the superclass method directly, past the subclass's override. The subclass the container and `vauban:generate` generate, and the processor's bytecode subclass, now declare a bridge `tag(Object)` that calls `tag(String)` virtually, as javac gives the processor's source subclass (BUG-20261118-18).
* **A client proxy generated as bytecode forwards a bridge to a superclass method.** A normal-scoped bean that inherits `String tag(String)` from a superclass and implements `Tagged<String>`, whose `tag(T)` that method implements, ran a call typed by `Tagged` on the proxy instance. javac implements the interface method through a bridge `tag(Object)` that calls the superclass method directly, past the proxy's override. The proxies the container and `vauban:generate` generate, and the processor's bytecode proxies, now forward that bridge too; the processor's source proxies were right (BUG-20261118-17).
* **An intercepted subclass generated at run time intercepts a public method of a non-public superclass.** A bean compiled without the annotation processor that inherits `public String get()` from a package-private superclass was not intercepted on that method: javac lists a bridge in its place, and the container's walk skipped bridges. It now takes the method the bridge copies, as the processor does (BUG-20261118-16). See xref:internals.adoc#intercepted-methods[Which methods the intercepted subclass covers].
* **A client proxy generated from a class file forwards a method that has a bridge.** A normal-scoped bean whose proxy is generated at run time, or by `vauban:generate`, ran some calls on the proxy itself, neither on the contextual instance nor through its interceptors: `String get()` of a bean that implements `Supplier<String>`, a covariant override such as `String name()` over `CharSequence name()`, and a public method a public class inherits from a package-private one. The bridge javac adds next to such a method took its place in the proxy's walk and was then left out, with the method. Those proxies are the ones of a class compiled without the annotation processor: a jar on the class path or the module path, an Arquillian or TCK deployment, a class an extension adds at start, a synthetic bean of a class. The walk over a class file now passes bridges by and reads each method as a member of the proxied class, as the processor does (BUG-20261117-49). See xref:internals.adoc#proxy-strategies[Client proxies].
* **A produced class with a `final` method next to its bridge is unproxyable on every path.** `public final String get()` in a class that implements `Supplier<String>` sits next to the bridge `Object get()`, which is not final: `vauban:generate`, the dependency enhancer and the container judged the bridge and found the class proxyable, where the annotation processor did not. They now agree with it (CDI 4.1 §3.10). `vauban:generate` and the dependency enhancer warn that the producer of such a class is not build-time proxyable and write no proxy, where they wrote one that could not override the method. At start, a normal-scoped producer of such a class whose package Vauban cannot define into, a class of the JDK or of a module that does not open the package to Vauban, fails the deployment with a `DeploymentException` that names the reason, where the start succeeded and the first call threw `UnproxyableResolutionException` or ran on the proxy (BUG-20261117-49). See xref:migration.adoc#upgrading[Migration].
* **An invoker looks its arguments up as an injection point.** An argument lookup (`withArgumentLookup`) of a `Holder<String>` parameter resolved the erased class `Holder` with `@Default`: it threw `UnsatisfiedResolutionException` for a bean of `Holder<String>`, and ignored the qualifiers of the parameter. It now resolves the declared type of the parameter with its qualifiers, under the rules of an injection point, and the start, or the build, checks each lookup by those rules, with the qualifiers extensions register: it refuses with a `DeploymentException` a lookup no bean satisfies, an ambiguous one, and a parameter whose type is a type variable, which was looked up by its bound, and no longer refuses a lookup a producer, a qualifier or a synthetic bean settles (BUG-20261117-27, BUG-20261117-39).
* **What changes: a raw bean type satisfies only the parameterizations CDI allows** (BUG-20261117-16).
+
*What changed.* CDI 4.1, 5.2.4: "A raw bean type is considered assignable to a parameterized required type if the raw types are identical and all type parameters of the required type are either unbounded type variables or `java.lang.Object`." The resolution of an injection point, at build, at start and frozen, and `BeanManager.getBeans`, `getReference` and `isMatchingBean` now apply one rule set, read as Weld reads it:
+
** A producer of a raw `Foo`, `@Produces Foo foo()` with `Foo<T>` generic, satisfies `@Inject Foo<Object>`, and no other `Foo<X>`, nor `Foo<?>`. It satisfied `@Inject Foo<Integer>`.
** A raw required type is satisfied by a `Foo<T>` bean type only when `T` declares no bound but `Object`: a bean of `Repo<T extends Number>` satisfies no raw `@Inject Repo` nor `VaubanContainer.select(Repo.class)`, as `BeanManager.getBeans(Repo.class)` already did not, and `T extends U` counts as bounded.
** A bean of a generic class has its class with its type variables among its bean types, `Repo<T>` for `class Repo<T>`, as `Bean.getTypes()` has it. It still satisfies `@Inject Repo<String>`.
** A type variable bounded by another is read up to its uppermost bound: `Chained<U extends Number, T extends U> implements Holder<T>` satisfies `@Inject Holder<Integer>`, which the start validated and the injection then refused.
+
*The messages.* The build fails when `Foo` is a class, the two qualifiers in either order:
+
----
[Vauban] Unsatisfied dependency: field Reader.injected of type ParameterizedType[rawType=vi.types.Foo, typeArguments=[ClassType[name=java.lang.Integer]]] with qualifiers [QualifierInstance[annotationName=jakarta.enterprise.inject.Any, members={}], QualifierInstance[annotationName=jakarta.enterprise.inject.Default, members={}]]
----
+
When `Foo` is an interface, the build warns with the same text followed by ` — the required type is not declared by this compilation unit; resolution deferred to the runtime container.`, and the start, extensions run or frozen, throws a `jakarta.enterprise.inject.spi.DeploymentException`:
+
----
CDI deployment validation failed:

*The ways out.*
+
** For a raw producer: give it its parameterized return type, `@Produces Foo<Integer> foo()`, or inject the raw type, `@Inject Foo`.

** For an observer's, a disposer's or a producer method's parameter of a type variable: declare it of its bound, `Gadget gadget`, or move the method to a subclass that gives the type variable a class.

* **Sessions survive a Vidocq dev swap.** When Vidocq swaps the application layer in dev mode, Foy writes each attribute of the live sessions with Java serialization and reads it back in the new layer (https://codefloe.com/Vidocq/foy/pulls/114[foy#114^]), inside `io.vidocq.vauban.api.Passivation.importInto(beanManager, importer)`, which binds the importing container for the serial forms to find. A `@SessionScoped` instance moves as its bean's passivation id and its state, with no `@PostConstruct` and no `@PreDestroy`. The client proxies it holds read back as the importing container's proxies of the same beans, and the built-in `Event`, `Instance` and `BeanManager` it injected as the importing container's own: an `Event` reaches the new observers, an `Instance` resolves the new beans. Every managed bean is now `PassivationCapable`, producer and synthetic beans included (the built-in beans are not), its id its `BeanId`, so a session attribute keeps its key from one container to the next. `SessionStore.isSession(Object)` lets a web container keep the session object itself out of the stream: Foy's `HttpSession` bean is produced again in the new layer. What cannot move keeps its session behind, with a `WARNING` that names the cause: a session bean that is not `Serializable` or is intercepted, an `Event` or an `Instance` obtained by `select(...)` or by a programmatic lookup, or given to a parameter of an observer method or of a producer method, an injected `InjectionPoint`, the `java.lang.reflect.Proxy` fallback of an interface. The limits: a synthetic bean's id follows its registration slot, a field added since reads back with its default value, and the `@PreDestroy` of a moved `@Dependent` object does not run. Passivation is still not validated at deployment, and CDI Lite stays at 774/774. See xref:internals.adoc#session-swap[Session entries across a container swap].
* **Overloaded producer methods deploy.** Two producer methods of one name, such as `@Produces Spoon make()` and `@Produces Fork make(Spoon spoon)`, failed the deployment as an illegal circular dependency: they shared one id, `Class#method`, and the container found each by its name alone. Each one now has an id of its own, `Class#method(T1,T2)` with its erased parameter types, and the container calls the right method; a producer method whose name no other producer method of its class has keeps `Class#method` (BUG-20261116-11). See xref:internals.adoc#session-swap[Session entries across a container swap].
* **A `Provider` injection point resolves.** `getInjectableReference` for a `Provider<Shelf>` injection point threw `UnsatisfiedResolutionException`, and `getBeans` found no bean for a `Provider<X>`: the built-in `Instance` bean is now a `Provider` too, as CDI 4.1 §5.6.2 says (BUG-20261116-10). See xref:internals.adoc#session-swap[Session entries across a container swap].
* **`Instance.select` keeps a parameterized type.** `select(new TypeLiteral<Supplier<String>>() { })` threw `ClassCastException`: it took a class literal only. And `select(qualifiers)` on an `Instance<Supplier<String>>` resolved the raw `Supplier`. The child `Instance` now resolves its beans with the whole type, as an injected `Instance<Supplier<String>>` does (BUG-20261116-09). See xref:usage.adoc#programmatic-instance[Programmatic `Instance<T>`].
* **`InjectionPoint.getBean()` names the class's own bean, not a producer it declares.** When a producer the class declares was registered before the class's managed bean, the injection points of the class belonged to the producer, and an `Event` or an `Instance` they gave moved with the producer's passivation id (BUG-20261116-08). See xref:internals.adoc#session-swap[Session entries across a container swap].
* **`getInjectableReference` gives the `Event` or the `Instance` an injection gives.** For an `Instance<Shelf>` injection point it gave an `Instance<Object>`, whose `get()` was ambiguous, and for a `@Loud Event<Ping>` one an `Event` that fired with `@Default` only. `getReference` of the built-in `Instance` bean for `Instance<Shelf>` lost the type too, and a qualified `Event` parameter of an observer method its qualifiers. They now carry the type and the qualifiers of the injection point. `getReference`, a lookup with no injection point, gives the requested type with `@Default`, and the `get()` of an `Instance<Event<Ping>>` an `Event` with the `Instance`'s qualifiers; such an `Event` fires with no injection point in its metadata. An interceptor the container creates by itself, outside the bean path, keeps the qualifiers of its `Event` or `Instance` constructor parameters (BUG-20261116-07). See xref:internals.adoc#session-swap[Session entries across a container swap].
* **An application whose archives were all processed at compile runs no extension at start, in a Vauban class loader and on the module path too.** Each archive the annotation processor handled carries the `vauban-bce-processed` marker, and when every bean archive does, the start skips the build compatible extensions. Under the Vauban class loader, the loader of a packaged Vidocq application, and on the module path, the start never recognised a jar as marked: the marker's URL (`jar:file:///app.jar!/…`) and the code source of the jar's classes (`file:/app.jar`) spell one file differently, and the container compared them as strings. So the extensions ran at every start, and with `vidocq.startup.require-frozen-extensions=true` the application refused to start. A module-path deployment of marked jars now skips its extensions at start too, as a class path or a directory of classes already did. The container compares locations as paths, a space or a non-ASCII character in the path included (BUG-20261115-07). The build of such an application no longer says that it has no build compatible extension: `vauban:generate` and `vidocq:generate` say `nothing to freeze: every build compatible extension of the deployment ran at compile`. See xref:internals.adoc#generated-code[Generated code and reflective fallback] and xref:concepts.adoc#frozen-extensions[Extensions frozen at build].
* **An encrypted jar in a directory whose name holds a space is found.** The start read the jar's path from its URL without decoding it, so an encrypted jar under `with space/` or a directory with a non-ASCII character was not found, and its beans were left out with a warning (BUG-20261115-08). See xref:internals.adoc#_class_loading[Class loading].
* **No "created in the last round" warning in a module whose only processor is Vauban.** javac starts an annotation processing round only for the files the previous one created: without another processor writing a class in the first round, the second round was javac's last, and every class Vauban wrote there, a client proxy, `_VaubanComponents`, cost a warning, six at each build of `foy-cdi-vauban`. A round the processor waits in now writes a compilation unit that declares no type, `_VaubanRound<n>.java`, and the processor writes its classes in the next round. A servlet secured with `@ServletSecurity`, an `@Inherited` annotation no processor starts from, no longer keeps the last round either. See xref:reference.adoc#generation-round[`-Avauban.generationRound`].
* **The "NOT on the annotation-processor path" warning says what it cannot see.** The processor reads one `META-INF/services` file of the class path, the first one, and never one in a jar, so extensions declared by the other entries were neither reported nor mentioned. When it found a file, the warning and the hint of an unsatisfied dependency now name that entry (the module's own output, when Maven puts it first) and say that the others cannot be checked, with the way to make them run: `<annotationProcessorPaths>` or the module path. See xref:concepts.adoc#extension-not-on-processor-path[Build Compatible Extensions].
* **No "NOT on the annotation-processor path" warning for a module's own extension.** A module that provides a build compatible extension, as `foy-cdi-vauban` provides `FoyWebExtension`, warned at its own build that the extension would not run, with advice that could not be followed: Maven puts the module's output, its service file included, on the class path. The processor no longer reports a type it compiles; another module's extension missing from the processor path is still reported. See xref:concepts.adoc#extension-not-on-processor-path[Build Compatible Extensions].
* **A bean module the application does not read satisfies its injection points at build.** An application that injects `HttpServletRequest`, `HttpSession` or `ServletContext` warned at every build that the type was unsatisfied and its resolution deferred to the container: javac only shows the processor the modules the compilation reads, and no module of a Vidocq application requires `io.vidocq.foy.cdi.vauban`, which produces them. The processor now also reads the bean archives on the processor path, where the extension's `-codegen` bundle puts that jar, from their `vauban-beans.list` and class files. See xref:reference.adoc#beans-of-other-modules[Injection points satisfied by another module].
* **Each module of a Vauban layer reads its own resources.** `Module.getResourceAsStream`, and `Class.getResource` on a class of a layer module, returned the first archive's copy of a name outside any package, whichever module asked: a runtime that reads one `META-INF/` descriptor from each module of the layer read the same file every time. The class loader now looks the resource up in the archive of the module that asks, and answers `null` when that module does not hold it, as the JDK's own loaders do; `Class.forName(Module, name)` likewise finds only that module's classes. The loader's own `getResource` and `getResources` still search every archive (BUG-20261114-05). See xref:internals.adoc#module-scoped-lookups[Class loading].
* **No client proxy for the `@Dependent` holder of a producer.** `vauban:generate` wrote a `<Holder>_ClientProxy` for a `@Dependent` class declaring a normal-scoped producer, as if the holder were the normal-scoped bean: a class nothing loads, counted among the generated proxies. A normal-scoped producer is proxied through the class it produces, and its holder gets a proxy of its own only when it is normal-scoped itself, as the annotation processor already did (BUG-20261114-03). See xref:usage.adoc#which-proxy[Which proxy do I get].
* **A class recompiled under a woven client proxy is woven at load.** A bean class your IDE recompiled over a Maven build, `javac -proc:none` style, lost the `(ProxyLink)` constructor its shipped client proxy calls; the start saw its no-arg constructor, wove nothing, and the first request threw `NoSuchMethodError`. The container now reads what that proxy calls and weaves the class at load, in the agent tier as in a Vauban layer; when nothing can weave it (the agent cannot be attached, or `-Dvauban.weaving.loadtime=disabled`), the start fails and names the bean and the reason. See xref:internals.adoc#recompiled-under-woven-proxy[A class recompiled under a woven proxy].
* **A normal-scoped producer of an abstract class gets its client proxy.** CDI 4.1 §3.10 does not count an abstract class as unproxyable, and Vauban no longer does: `@Produces @ApplicationScoped Clock` works. The processor and `vauban:generate` generate the proxy at build time in the producer's package, forwarding every method to what the producer returns, the abstract ones included; `vauban:enhance-dependencies` no longer refuses an abstract type. Without a build step, the container defines the same proxy in the producer's package when it cannot define a class in the produced type's own (a class of the JDK, a package not opened to it), where it used to fail with a `NullPointerException`; a type no proxy can serve is a `DeploymentException` that names it and suggests `@Singleton` or `@Dependent` (BUG-20261114-02). See xref:usage.adoc#which-proxy[Which proxy do I get].
* **Build-time client proxies for synthetic beans.** An extension lists in `@ClientProxies` the interfaces of the normal-scoped synthetic beans it registers, and the processor generates their client proxies: no `java.lang.reflect.Proxy` at boot, no reflection on each call. The boot warning names such a proxy apart and gives this advice. See xref:concepts.adoc#synthetic-interface-proxies[Client proxies of synthetic beans].
* **A startup observer reaches every scope.** The contexts build compatible extensions register are installed before `@Initialized(ApplicationScoped.class)` and `Startup` fire, so an observer of those events can call a bean of such a scope, a `@TransactionScoped` bean among them. See xref:usage.adoc#startup-events[The startup events].
* **Extensions frozen at build.** A build step that sees the whole deployment (`vauban:generate` with `freezeExtensions`) runs the build compatible extensions once and records what they did; the container start of that deployment loads the record instead of running them, 30 to 40 ms less on a 425 ms start of an application with ten extensions (BENCH-20261113-01). An extension that left work for the start runs again at start, and any deployment that is not the one frozen runs its extensions as before. See xref:concepts.adoc#frozen-extensions[Extensions frozen at build] and xref:concepts.adoc#writing-a-frozen-extension[Writing an extension the build can freeze].
* **A `Startup` observer can refuse the deployment.** A `DeploymentException` or `DefinitionException` it throws stops the start as it is, unwrapped. See xref:usage.adoc#lifecycle-observer-failures[When a lifecycle observer throws].
* **`VaubanContainerBuilder.addHostBean`** adds a bean of the embedding runtime that leaves a frozen deployment valid, and **`VaubanContainer.extensionsAtStart()`** says what the start did with the extensions. When the record of a build is refused, its note names the bean classes added, removed or changed since that build. See xref:concepts.adoc#frozen-extensions[Extensions frozen at build].
