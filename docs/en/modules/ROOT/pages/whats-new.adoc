= What's new
:description: Everything that changed in this component since the {release-version} release.

[.lead]
New in the `{project-version}` development line — everything listed here landed **after the {release-version} release** and is not part of it. Every entry links to the section that documents it, and those sections carry the [.tag-new]#NEW# badge. Each brick of the suite keeps its own page of this kind; xref:home::whats-new.adoc[the ecosystem index] gathers them. When the next release train ships, this page is frozen with it and restarts empty on the dev line.

* **An invoker looks its arguments up as an injection point.** An argument lookup (`withArgumentLookup`) of a `Holder<String>` parameter resolved the erased class `Holder` with `@Default`: it threw `UnsatisfiedResolutionException` for a bean of `Holder<String>`, and ignored the qualifiers of the parameter. It now resolves the declared type of the parameter with its qualifiers, under the rules of an injection point, and the start, or the build, checks each lookup by those rules, with the qualifiers extensions register: it refuses with a `DeploymentException` a lookup no bean satisfies, an ambiguous one, and a parameter whose type is a type variable, which was looked up by its bound, and no longer refuses a lookup a producer, a qualifier or a synthetic bean settles (BUG-20261117-27, BUG-20261117-39).
* **What changes: a raw bean type satisfies only the parameterizations CDI allows** (BUG-20261117-16).
+
*What changed.* CDI 4.1, 5.2.4: "A raw bean type is considered assignable to a parameterized required type if the raw types are identical and all type parameters of the required type are either unbounded type variables or `java.lang.Object`." The resolution of an injection point, at build, at start and frozen, and `BeanManager.getBeans`, `getReference` and `isMatchingBean` now apply one rule set, read as Weld reads it:
+
** A producer of a raw `Foo`, `@Produces Foo foo()` with `Foo<T>` generic, satisfies `@Inject Foo<Object>`, and no other `Foo<X>`, nor `Foo<?>`. It satisfied `@Inject Foo<Integer>`.
** A raw required type is satisfied by a `Foo<T>` bean type only when `T` declares no bound but `Object`: a bean of `Repo<T extends Number>` satisfies no raw `@Inject Repo` nor `VaubanContainer.select(Repo.class)`, as `BeanManager.getBeans(Repo.class)` already did not, and `T extends U` counts as bounded.
** A bean of a generic class has its class with its type variables among its bean types, `Repo<T>` for `class Repo<T>`, as `Bean.getTypes()` has it. It still satisfies `@Inject Repo<String>`.
** A type variable bounded by another is read up to its uppermost bound: `Chained<U extends Number, T extends U> implements Holder<T>` satisfies `@Inject Holder<Integer>`, which the start validated and the injection then refused.
+
*The messages.* The build fails when `Foo` is a class, the two qualifiers in either order:
+
----
[Vauban] Unsatisfied dependency: field Reader.injected of type ParameterizedType[rawType=vi.types.Foo, typeArguments=[ClassType[name=java.lang.Integer]]] with qualifiers [QualifierInstance[annotationName=jakarta.enterprise.inject.Any, members={}], QualifierInstance[annotationName=jakarta.enterprise.inject.Default, members={}]]
----
+
When `Foo` is an interface, the build warns with the same text followed by ` — the required type is not declared by this compilation unit; resolution deferred to the runtime container.`, and the start, extensions run or frozen, throws a `jakarta.enterprise.inject.spi.DeploymentException`:
+
----
CDI deployment validation failed:
  - Unsatisfied dependency: field Reader.injected of type ParameterizedType[rawType=vi.types.Foo, typeArguments=[ClassType[name=java.lang.Integer]]] with qualifiers [QualifierInstance[annotationName=jakarta.enterprise.inject.Any, members={}], QualifierInstance[annotationName=jakarta.enterprise.inject.Default, members={}]]
----
+
*Who is affected.*
+
** An application that injects a parameterization of a type that only a raw producer produces.
** An application that injects or selects a bean of a bounded generic class by its raw class. A bounded generic `@Dependent` Cassini resource or provider, which Cassini looks up by its class, now fails at request time with `IllegalArgumentException: Not managed by Vauban: ...` (`VaubanBeanProvider.getBean`).
** An injection point of a producer of an inner class of a generic class, `@Inject Holder<String>` for a producer of `Outer<String>.Inner<Integer>` where `Inner<I> implements Holder<O>`, resolved through the old rule only: it is unsatisfied at build and at start until BUG-20261117-21 is fixed.
** A bean whose observer method has a parameter besides the event parameter, whose disposer method has one besides the disposed parameter, or whose producer method has one, `… sprocket producer param 0`, of a type variable of its class: `void dispose(@Disposes Widget widget, T gadget)` in `WidgetFactory<T extends Gadget>`. Such a parameter is an injection point, and an injection point of a type variable is a definition error (CDI 4.1, 5.2.3). The build warns:
+
----
WARNING: [Vauban] Injection point has type variable type T: vi.types.WidgetFactory.dispose disposer param 1 — the container rejects this deployment at start.
----
+
and the start, and the build's freeze, refuse the deployment with a `jakarta.enterprise.inject.spi.DefinitionException`:
+
----
CDI definition validation failed:
  - Injection point has type variable type T: vi.types.WidgetFactory.dispose disposer param 1
----
+
An observer a bean inherits from an abstract or vetoed class, whose type variable the bean class gives a class, is not concerned. The start looked a disposer's parameter of a type variable up by its erased class, `Gadget`, and checked an observer's not at all.
+
*The ways out.*
+
** For a raw producer: give it its parameterized return type, `@Produces Foo<Integer> foo()`, or inject the raw type, `@Inject Foo`.
** For a bounded generic class: inject or look up a parameterization within the bound, `@Inject Repo<Integer>` or `select(new TypeLiteral<Repo<Integer>>() {})`, or declare the type variable unbounded.
** For an observer's, a disposer's or a producer method's parameter of a type variable: declare it of its bound, `Gadget gadget`, or move the method to a subclass that gives the type variable a class.
+
Fixed with it: a `@Typed` producer keeps the parameterized forms of the types it names (BUG-20261117-19); a bean's type variable meets a wildcard and an actual type within its bound (BUG-20261117-24); an observer's or a disposer's parameter is checked, resolved and named by its parameterized type, `Holder<java.lang.Integer>` (BUG-20261117-25). See xref:migration.adoc#upgrading[Upgrading from Vauban {release-version}].
* **An extension sees the type arguments of a class's supertypes.** `ClassInfo.superClass()` and `superInterfaces()` gave every supertype raw: for `interface Archive extends Crud<Note, Long>, Labelled<List<String>>`, an extension saw the classes `Crud` and `Labelled`, and could not give a synthetic bean the types an `@Inject Crud<Note, Long>` needs. They now give the supertypes as the class declares them, in the processor, at start and frozen: `Crud<Note, Long>` then `Labelled<List<String>>`. A type argument may be a class, a parameterized type, an array or a type variable, and wildcards may appear inside one, as in `Holder<List<? extends Number>>`: Java allows no wildcard as a type argument of a supertype itself (JLS 8.1.4). A supertype the class names raw stays a class. An interface's `superClass()` is now `null` at start too, as the language model asks and the processor already gave it. Wherever the language model shows a wildcard `?`, in a supertype, a field, a parameter or a bean type, its upper bound is now `java.lang.Object`, as the language model asks: it had none, and the processor gave `? extends Object` one, the start not. A class outside the deployment, such as Jakarta Data's `CrudRepository` in a jar or the JDK's `Supplier`, is now described as the index describes its own classes, whichever way an extension reaches it, at start and frozen from its class file and in the processor from the compilation: it was a stub, with no type parameter and no supertype but `java.lang.Object`, at start and frozen, and in the processor for a JDK class; `superClassDeclaration()` and `superInterfacesDeclarations()` stopped at the index, and `AnnotationInfo.declaration()` threw at start for an annotation type outside it (BUG-20261117-31). For a class nothing describes, no class file and no class of the compilation, they keep those answers, so that an extension keeps its "I cannot see this class" path. See xref:concepts.adoc#language-model[Build Compatible Extensions].
* **An extension sees the type parameters of a method.** `MethodInfo.typeParameters()` was always empty. It now gives the type parameters a generic method declares, with their bounds, in the processor, at start and frozen, as `ClassInfo.typeParameters()` gives a class's; a bound may name a type variable of the class (BUG-20261117-51). See xref:concepts.adoc#language-model[Build Compatible Extensions].
* **An extension sees a thrown type variable at start.** For `<F extends Throwable> void run() throws E, F`, `MethodInfo.throwsTypes()` gave the classes `Exception` and `Throwable` at start and frozen, the erasures the class file names; it now gives the type variables `E` and `F`, with their bounds, as the processor did (BUG-20261117-52). See xref:concepts.adoc#language-model[Build Compatible Extensions].
* **A compilation no longer overflows the stack on a type variable bounded by itself.** The annotation processor failed with a `StackOverflowError` on a field, a parameter or a return of a type variable bounded by itself, `T` in `class Box<T extends Comparable<T>>` say. Inside its own bound, such a variable now has no bound, as the bytecode scan records it (BUG-20261117-36). See xref:concepts.adoc#language-model[Build Compatible Extensions].
* **The synthetic metadata file is the same at every build.** `META-INF/vauban-synthetic-metadata.properties` carried the date `Properties.store` writes, so a build tool that watched it, the `vidocq:dev` loop among them, saw a change at every compile and swapped the whole layer instead of redefining the class. It is written without the date and with its keys sorted; a file of an earlier version still reads. See xref:concepts.adoc[Concepts].
* **The build gives a bean the types a class it compiles brings.** In an application compiled with the annotation processor, a bean that extends a class the compilation compiles and no annotation brings into the index, an abstract class say, lacked the classes and interfaces above that class: `vi.SerialService extends vi.Wrapping`, where `Wrapping implements Serializable`, was no `Serializable` to the extensions the processor ran nor to the injection points the build resolved. An `@Inject @Serial Serializable` that only it satisfies failed the build as unsatisfied, two such beans passed the build and were refused at start as ambiguous, and `@Registration(types = Serializable.class)` was not called for it. The container saw those types at start. The processor now reads those classes from its own description of the compilation, around its bean discovery as around the extension phases; the container already read them at start, by loading the classes (BUG-20261117-03). The client proxy the processor generates for a normal-scoped producer is the proxy the container looks up: the produced type, or for a `@Typed` producer the first type of the `@Typed` the container meets above it; it could be the proxy of another class or interface above it, a different one from one build to the next (BUG-20261117-15). Those types, the types a bean of the compilation declares, `Callable<String>` say, and those above a producer's type, `Box<String>` say, carry their type arguments, as at start: they were raw, and a raw type matched every parameterization, so an injection point of `Callable<String>` or `Repo<String>` that two beans reach with different type arguments was reported ambiguous at build. What changes at start, and in the extensions frozen at build: the container resolves a type variable inside a wildcard, an array and the class that encloses an inner class, as the compiler does, so a bean of `ArrayShelf<S> implements Holder<S[]>` given `String` is a `Holder<String[]>` and satisfies an injection point of it, which the start refused. A type that is no legal bean type, one with a wildcard type argument or with a type variable of a class above the bean's class, which only a supertype named raw leaves there, is no longer among the types an extension sees for a bean, as it never was in `Bean.getTypes()`. For the second, the bean has its raw class instead, in both, as Java erases the types above a raw type: a bean of `LegacyNames extends ArrayList`, raw, is a `List` in `Bean.getTypes()` too, which dropped `List<E>` and its class with it, and a producer of it no longer has `List<E>` there, but `List`. A type argument of a produced type that is not a class keeps its shape in the types above it, at build as at start: a producer of `Box<List<String>>`, where `Box<T> implements Repo<T>`, is a `Repo<List<String>>`, and no longer a `Box<Object>` and a `Repo<Object>`, as the start gave it, and a producer of `<T> Box<T>` is a `Repo<T>`, where the build gave it the raw `Repo` (BUG-20261117-14, BUG-20261117-17). A primitive type matches the class named after it whatever the default locale: under a Turkish one, `int` and an array of `int` no longer matched (BUG-20261117-20). See xref:concepts.adoc#classes-outside-the-index[Build Compatible Extensions].
* **The annotation processor runs from a processor module path.** javac given `vauban-processor` on `--processor-module-path`, in a JVM whose module path holds `vauban-core`, defines the processor's module in a layer above vauban-core's, which the packages vauban-core exports to the processor alone do not reach: a compilation with a normal-scoped bean, or with an intercepted method that carries an annotation, failed with `IllegalAccessError`. The processor now gets them from vauban-core when it starts. A build with Maven's `annotationProcessorPaths`, the `vidocq:dev` loop included, puts the processor on a class path and was not affected (BUG-20261117-23). See xref:reference.adoc[Reference].
* **An extension the annotation processor runs sees the interceptors and the observers the compilation compiles.** `@Registration` matched an interceptor, and an observer, by loading its class through the processor's class loader, where a class the compilation compiles does not load: the processor called `@Registration(types = Object.class)` for the beans of the compilation and for none of its interceptors, and an `ObserverInfo` method for none of its observers. The container called them, whether the extensions ran at start or the build froze them. The processor now reads the class and those above it from the index and from its own description of the compilation; a class neither describes, one of the JDK say, is loaded as before. `@Enhancement(withSubtypes = true)` read the classes above a class otherwise, through the superclasses the index holds and the interfaces the class declares itself: in the processor it missed a class that has an expected type through a class it extends that carries no annotation, or through an interface of an interface, which the container finds at start; it now reads them the same way (BUG-20261117-07). A method with an `InterceptorInfo` parameter is called for the interceptors only, as CDI 4.1 says: it was handed every bean too, and the deployment failed with "argument type mismatch", at start as at build. A method with an `ObserverInfo` parameter is called for each observer whose observed event type is assignable to one of its `types`, arrays, type variables and primitive types included, where the container matched the class that declares the observer (BUG-20261117-02, BUG-20261117-05). See xref:concepts.adoc#registration-at-build[Build Compatible Extensions].
* **A package-level `@Vetoed` holds however a class reaches the deployment.** The classes of a package whose `package-info.java` is annotated `@Vetoed` were beans, and an interceptor among them intercepted, in an application compiled with the annotation processor, in a `beans.xml` archive no Vauban build step processed, a directory or a jar, in a package `scanPackage` scans, and when an extension added them through `ScannedClasses`. The container reads a package's veto on its `package-info` class, which none of these paths brought to it. The processor now reads the package's `@Vetoed` and leaves its classes out of `vauban-beans.list`, and generates no client proxy, no `$$Intercepted` subclass and no `_VaubanComponents` for them; an injection point that needs one of them is unsatisfied at build, as at start, and no bean of a vetoed package of another module satisfies one at build. The container looks up the `package-info` of the package of each class it indexes, whatever way the class came, a `vauban-beans.list` written by an earlier processor included. `vauban:generate` already read it from the class files. An extension's `@Registration` sees nothing of a vetoed package, whether the extensions run at start or the build froze them, and no extension phase is given a `package-info` as a type any more: `@Enhancement(types = Object.class)` was given the `package-info` of every annotated package of an archive (BUG-20261117-01). See xref:usage.adoc#vetoed-interceptor[Interceptors].
* **A vetoed interceptor intercepts nothing.** An interceptor class annotated `@Vetoed`, or a class of a package annotated `@Vetoed`, was no bean, but it still intercepted the beans its binding names, and an extension's `@Registration` saw it as an interceptor: the container made an interceptor of every class annotated `@Interceptor`. CDI 4.1 ignores a vetoed type altogether, and the container now leaves it out of its interceptors too, whether the extensions run at start or the build froze them. An application compiled with the annotation processor already left a vetoed class out. The `$$Intercepted` subclasses the build generates need no change: they run the chain the container resolves (BUG-20261116-12). See xref:usage.adoc#vetoed-interceptor[Interceptors].
* **Sessions survive a Vidocq dev swap.** When Vidocq swaps the application layer in dev mode, Foy writes each attribute of the live sessions with Java serialization and reads it back in the new layer (https://codefloe.com/Vidocq/foy/pulls/114[foy#114^]), inside `io.vidocq.vauban.api.Passivation.importInto(beanManager, importer)`, which binds the importing container for the serial forms to find. A `@SessionScoped` instance moves as its bean's passivation id and its state, with no `@PostConstruct` and no `@PreDestroy`. The client proxies it holds read back as the importing container's proxies of the same beans, and the built-in `Event`, `Instance` and `BeanManager` it injected as the importing container's own: an `Event` reaches the new observers, an `Instance` resolves the new beans. Every managed bean is now `PassivationCapable`, producer and synthetic beans included (the built-in beans are not), its id its `BeanId`, so a session attribute keeps its key from one container to the next. `SessionStore.isSession(Object)` lets a web container keep the session object itself out of the stream: Foy's `HttpSession` bean is produced again in the new layer. What cannot move keeps its session behind, with a `WARNING` that names the cause: a session bean that is not `Serializable` or is intercepted, an `Event` or an `Instance` obtained by `select(...)` or by a programmatic lookup, or given to a parameter of an observer method or of a producer method, an injected `InjectionPoint`, the `java.lang.reflect.Proxy` fallback of an interface. The limits: a synthetic bean's id follows its registration slot, a field added since reads back with its default value, and the `@PreDestroy` of a moved `@Dependent` object does not run. Passivation is still not validated at deployment, and CDI Lite stays at 774/774. See xref:internals.adoc#session-swap[Session entries across a container swap].
* **Overloaded producer methods deploy.** Two producer methods of one name, such as `@Produces Spoon make()` and `@Produces Fork make(Spoon spoon)`, failed the deployment as an illegal circular dependency: they shared one id, `Class#method`, and the container found each by its name alone. Each one now has an id of its own, `Class#method(T1,T2)` with its erased parameter types, and the container calls the right method; a producer method whose name no other producer method of its class has keeps `Class#method` (BUG-20261116-11). See xref:internals.adoc#session-swap[Session entries across a container swap].
* **A `Provider` injection point resolves.** `getInjectableReference` for a `Provider<Shelf>` injection point threw `UnsatisfiedResolutionException`, and `getBeans` found no bean for a `Provider<X>`: the built-in `Instance` bean is now a `Provider` too, as CDI 4.1 §5.6.2 says (BUG-20261116-10). See xref:internals.adoc#session-swap[Session entries across a container swap].
* **`Instance.select` keeps a parameterized type.** `select(new TypeLiteral<Supplier<String>>() { })` threw `ClassCastException`: it took a class literal only. And `select(qualifiers)` on an `Instance<Supplier<String>>` resolved the raw `Supplier`. The child `Instance` now resolves its beans with the whole type, as an injected `Instance<Supplier<String>>` does (BUG-20261116-09). See xref:usage.adoc#programmatic-instance[Programmatic `Instance<T>`].
* **`InjectionPoint.getBean()` names the class's own bean, not a producer it declares.** When a producer the class declares was registered before the class's managed bean, the injection points of the class belonged to the producer, and an `Event` or an `Instance` they gave moved with the producer's passivation id (BUG-20261116-08). See xref:internals.adoc#session-swap[Session entries across a container swap].
* **`getInjectableReference` gives the `Event` or the `Instance` an injection gives.** For an `Instance<Shelf>` injection point it gave an `Instance<Object>`, whose `get()` was ambiguous, and for a `@Loud Event<Ping>` one an `Event` that fired with `@Default` only. `getReference` of the built-in `Instance` bean for `Instance<Shelf>` lost the type too, and a qualified `Event` parameter of an observer method its qualifiers. They now carry the type and the qualifiers of the injection point. `getReference`, a lookup with no injection point, gives the requested type with `@Default`, and the `get()` of an `Instance<Event<Ping>>` an `Event` with the `Instance`'s qualifiers; such an `Event` fires with no injection point in its metadata. An interceptor the container creates by itself, outside the bean path, keeps the qualifiers of its `Event` or `Instance` constructor parameters (BUG-20261116-07). See xref:internals.adoc#session-swap[Session entries across a container swap].
* **An application whose archives were all processed at compile runs no extension at start, in a Vauban class loader and on the module path too.** Each archive the annotation processor handled carries the `vauban-bce-processed` marker, and when every bean archive does, the start skips the build compatible extensions. Under the Vauban class loader, the loader of a packaged Vidocq application, and on the module path, the start never recognised a jar as marked: the marker's URL (`jar:file:///app.jar!/…`) and the code source of the jar's classes (`file:/app.jar`) spell one file differently, and the container compared them as strings. So the extensions ran at every start, and with `vidocq.startup.require-frozen-extensions=true` the application refused to start. A module-path deployment of marked jars now skips its extensions at start too, as a class path or a directory of classes already did. The container compares locations as paths, a space or a non-ASCII character in the path included (BUG-20261115-07). The build of such an application no longer says that it has no build compatible extension: `vauban:generate` and `vidocq:generate` say `nothing to freeze: every build compatible extension of the deployment ran at compile`. See xref:internals.adoc#generated-code[Generated code and reflective fallback] and xref:concepts.adoc#frozen-extensions[Extensions frozen at build].
* **An encrypted jar in a directory whose name holds a space is found.** The start read the jar's path from its URL without decoding it, so an encrypted jar under `with space/` or a directory with a non-ASCII character was not found, and its beans were left out with a warning (BUG-20261115-08). See xref:internals.adoc#_class_loading[Class loading].
* **No "created in the last round" warning in a module whose only processor is Vauban.** javac starts an annotation processing round only for the files the previous one created: without another processor writing a class in the first round, the second round was javac's last, and every class Vauban wrote there, a client proxy, `_VaubanComponents`, cost a warning, six at each build of `foy-cdi-vauban`. A round the processor waits in now writes a compilation unit that declares no type, `_VaubanRound<n>.java`, and the processor writes its classes in the next round. A servlet secured with `@ServletSecurity`, an `@Inherited` annotation no processor starts from, no longer keeps the last round either. See xref:reference.adoc#generation-round[`-Avauban.generationRound`].
* **The "NOT on the annotation-processor path" warning says what it cannot see.** The processor reads one `META-INF/services` file of the class path, the first one, and never one in a jar, so extensions declared by the other entries were neither reported nor mentioned. When it found a file, the warning and the hint of an unsatisfied dependency now name that entry (the module's own output, when Maven puts it first) and say that the others cannot be checked, with the way to make them run: `<annotationProcessorPaths>` or the module path. See xref:concepts.adoc#extension-not-on-processor-path[Build Compatible Extensions].
* **No "NOT on the annotation-processor path" warning for a module's own extension.** A module that provides a build compatible extension, as `foy-cdi-vauban` provides `FoyWebExtension`, warned at its own build that the extension would not run, with advice that could not be followed: Maven puts the module's output, its service file included, on the class path. The processor no longer reports a type it compiles; another module's extension missing from the processor path is still reported. See xref:concepts.adoc#extension-not-on-processor-path[Build Compatible Extensions].
* **A bean module the application does not read satisfies its injection points at build.** An application that injects `HttpServletRequest`, `HttpSession` or `ServletContext` warned at every build that the type was unsatisfied and its resolution deferred to the container: javac only shows the processor the modules the compilation reads, and no module of a Vidocq application requires `io.vidocq.foy.cdi.vauban`, which produces them. The processor now also reads the bean archives on the processor path, where the extension's `-codegen` bundle puts that jar, from their `vauban-beans.list` and class files. See xref:reference.adoc#beans-of-other-modules[Injection points satisfied by another module].
* **Each module of a Vauban layer reads its own resources.** `Module.getResourceAsStream`, and `Class.getResource` on a class of a layer module, returned the first archive's copy of a name outside any package, whichever module asked: a runtime that reads one `META-INF/` descriptor from each module of the layer read the same file every time. The class loader now looks the resource up in the archive of the module that asks, and answers `null` when that module does not hold it, as the JDK's own loaders do; `Class.forName(Module, name)` likewise finds only that module's classes. The loader's own `getResource` and `getResources` still search every archive (BUG-20261114-05). See xref:internals.adoc#module-scoped-lookups[Class loading].
* **No client proxy for the `@Dependent` holder of a producer.** `vauban:generate` wrote a `<Holder>_ClientProxy` for a `@Dependent` class declaring a normal-scoped producer, as if the holder were the normal-scoped bean: a class nothing loads, counted among the generated proxies. A normal-scoped producer is proxied through the class it produces, and its holder gets a proxy of its own only when it is normal-scoped itself, as the annotation processor already did (BUG-20261114-03). See xref:usage.adoc#which-proxy[Which proxy do I get].
* **A class recompiled under a woven client proxy is woven at load.** A bean class your IDE recompiled over a Maven build, `javac -proc:none` style, lost the `(ProxyLink)` constructor its shipped client proxy calls; the start saw its no-arg constructor, wove nothing, and the first request threw `NoSuchMethodError`. The container now reads what that proxy calls and weaves the class at load, in the agent tier as in a Vauban layer; when nothing can weave it (the agent cannot be attached, or `-Dvauban.weaving.loadtime=disabled`), the start fails and names the bean and the reason. See xref:internals.adoc#recompiled-under-woven-proxy[A class recompiled under a woven proxy].
* **A normal-scoped producer of an abstract class gets its client proxy.** CDI 4.1 §3.10 does not count an abstract class as unproxyable, and Vauban no longer does: `@Produces @ApplicationScoped Clock` works. The processor and `vauban:generate` generate the proxy at build time in the producer's package, forwarding every method to what the producer returns, the abstract ones included; `vauban:enhance-dependencies` no longer refuses an abstract type. Without a build step, the container defines the same proxy in the producer's package when it cannot define a class in the produced type's own (a class of the JDK, a package not opened to it), where it used to fail with a `NullPointerException`; a type no proxy can serve is a `DeploymentException` that names it and suggests `@Singleton` or `@Dependent` (BUG-20261114-02). See xref:usage.adoc#which-proxy[Which proxy do I get].
* **Build-time client proxies for synthetic beans.** An extension lists in `@ClientProxies` the interfaces of the normal-scoped synthetic beans it registers, and the processor generates their client proxies: no `java.lang.reflect.Proxy` at boot, no reflection on each call. The boot warning names such a proxy apart and gives this advice. See xref:concepts.adoc#synthetic-interface-proxies[Client proxies of synthetic beans].
* **A startup observer reaches every scope.** The contexts build compatible extensions register are installed before `@Initialized(ApplicationScoped.class)` and `Startup` fire, so an observer of those events can call a bean of such a scope, a `@TransactionScoped` bean among them. See xref:usage.adoc#startup-events[The startup events].
* **Extensions frozen at build.** A build step that sees the whole deployment (`vauban:generate` with `freezeExtensions`) runs the build compatible extensions once and records what they did; the container start of that deployment loads the record instead of running them, 30 to 40 ms less on a 425 ms start of an application with ten extensions (BENCH-20261113-01). An extension that left work for the start runs again at start, and any deployment that is not the one frozen runs its extensions as before. See xref:concepts.adoc#frozen-extensions[Extensions frozen at build] and xref:concepts.adoc#writing-a-frozen-extension[Writing an extension the build can freeze].
* **A `Startup` observer can refuse the deployment.** A `DeploymentException` or `DefinitionException` it throws stops the start as it is, unwrapped. See xref:usage.adoc#lifecycle-observer-failures[When a lifecycle observer throws].
* **`VaubanContainerBuilder.addHostBean`** adds a bean of the embedding runtime that leaves a frozen deployment valid, and **`VaubanContainer.extensionsAtStart()`** says what the start did with the extensions. When the record of a build is refused, its note names the bean classes added, removed or changed since that build. See xref:concepts.adoc#frozen-extensions[Extensions frozen at build].
