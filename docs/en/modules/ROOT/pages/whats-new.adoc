= What's new
:description: Everything that changed in this component since the {release-version} release.

[.lead]
New in the `{project-version}` development line — everything listed here landed **after the {release-version} release** and is not part of it. Every entry links to the section that documents it, and those sections carry the [.tag-new]#NEW# badge. Each brick of the suite keeps its own page of this kind; xref:home::whats-new.adoc[the ecosystem index] gathers them. When the next release train ships, this page is frozen with it and restarts empty on the dev line.

* **No client proxy for the `@Dependent` holder of a producer.** `vauban:generate` wrote a `<Holder>_ClientProxy` for a `@Dependent` class declaring a normal-scoped producer, as if the holder were the normal-scoped bean: a class nothing loads, counted among the generated proxies. A normal-scoped producer is proxied through the class it produces, and its holder gets a proxy of its own only when it is normal-scoped itself, as the annotation processor already did (BUG-20261114-03). See xref:usage.adoc#which-proxy[Which proxy do I get].
* **A class recompiled under a woven client proxy is woven at load.** A bean class your IDE recompiled over a Maven build, `javac -proc:none` style, lost the `(ProxyLink)` constructor its shipped client proxy calls; the start saw its no-arg constructor, wove nothing, and the first request threw `NoSuchMethodError`. The container now reads what that proxy calls and weaves the class at load, in the agent tier as in a Vauban layer; when nothing can weave it (the agent cannot be attached, or `-Dvauban.weaving.loadtime=disabled`), the start fails and names the bean and the reason. See xref:internals.adoc#recompiled-under-woven-proxy[A class recompiled under a woven proxy].
* **A normal-scoped producer of an abstract class gets its client proxy.** CDI 4.1 §3.10 does not count an abstract class as unproxyable, and Vauban no longer does: `@Produces @ApplicationScoped Clock` works. The processor and `vauban:generate` generate the proxy at build time in the producer's package, forwarding every method to what the producer returns, the abstract ones included; `vauban:enhance-dependencies` no longer refuses an abstract type. Without a build step, the container defines the same proxy in the producer's package when it cannot define a class in the produced type's own (a class of the JDK, a package not opened to it), where it used to fail with a `NullPointerException`; a type no proxy can serve is a `DeploymentException` that names it and suggests `@Singleton` or `@Dependent` (BUG-20261114-02). See xref:usage.adoc#which-proxy[Which proxy do I get].
* **Build-time client proxies for synthetic beans.** An extension lists in `@ClientProxies` the interfaces of the normal-scoped synthetic beans it registers, and the processor generates their client proxies: no `java.lang.reflect.Proxy` at boot, no reflection on each call. The boot warning names such a proxy apart and gives this advice. See xref:concepts.adoc#synthetic-interface-proxies[Client proxies of synthetic beans].
* **A startup observer reaches every scope.** The contexts build compatible extensions register are installed before `@Initialized(ApplicationScoped.class)` and `Startup` fire, so an observer of those events can call a bean of such a scope, a `@TransactionScoped` bean among them. See xref:usage.adoc#startup-events[The startup events].
* **Extensions frozen at build.** A build step that sees the whole deployment (`vauban:generate` with `freezeExtensions`) runs the build compatible extensions once and records what they did; the container start of that deployment loads the record instead of running them, 30 to 40 ms less on a 425 ms start of an application with ten extensions (BENCH-20261113-01). An extension that left work for the start runs again at start, and any deployment that is not the one frozen runs its extensions as before. See xref:concepts.adoc#frozen-extensions[Extensions frozen at build] and xref:concepts.adoc#writing-a-frozen-extension[Writing an extension the build can freeze].
* **A `Startup` observer can refuse the deployment.** A `DeploymentException` or `DefinitionException` it throws stops the start as it is, unwrapped. See xref:usage.adoc#lifecycle-observer-failures[When a lifecycle observer throws].
* **`VaubanContainerBuilder.addHostBean`** adds a bean of the embedding runtime that leaves a frozen deployment valid, and **`VaubanContainer.extensionsAtStart()`** says what the start did with the extensions. When the record of a build is refused, its note names the bean classes added, removed or changed since that build. See xref:concepts.adoc#frozen-extensions[Extensions frozen at build].
