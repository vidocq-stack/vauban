= What's new
:description: Everything that changed in Vauban since the {release-version} release — the Java SE launcher, client proxies without opens, the build tooling around them, the interception of inherited methods, extension support and the fixes that change behaviour.

[.lead]
New in the `{project-version}` development line — everything listed here landed **after the {release-version} release** and is not part of it. Every entry links to the section that documents it, and those sections carry the [.tag-new]#NEW# badge. Each brick of the suite keeps its own page of this kind; xref:home::whats-new.adoc[the ecosystem index] gathers them. When the next release train ships, this page is frozen with it and restarts empty on the dev line.

== Running inside a Vauban layer

The Java SE launcher, and what changes once Vauban's own class loader defines the application's classes:

* **Vauban in Java SE** — a page of its own for the SE container: which modules the launcher re-layers, why the entry point has to run inside the layer, the two resources the build ships, and the limits, from a bare boot layer to GraalVM `native-image`, which is not supported. `SeContainerInitializer` itself works as the specification describes, on the module path, with no configuration. xref:se.adoc[Vauban in Java SE].
* **Java SE launcher** — `java -p mods --add-modules ALL-MODULE-PATH -m io.vidocq.vauban.classloader/io.vidocq.vauban.classloader.Launch <module>/<main-class>` runs the application inside a Vauban layer. `--add-modules ALL-MODULE-PATH` is required, since `-m` makes the launcher the only root module. `Launch.run(target, args)` is the programmatic form and returns `false`, doing nothing, when the thread already runs in a layer. It ships as `io.vidocq.vauban:vauban-classloader`, at `runtime` scope. xref:se.adoc#the-launcher[The launcher], xref:reference.adoc#maven-artefacts[Maven artefacts].
* **`-Dvauban.launch.keep=<prefixes>`** — module-name prefixes the launcher keeps in the boot layer, on top of the built-in rules, for a test framework or an agent-attached library that must not move. A named target module is a root, so no keep prefix can hold the application itself back. xref:se.adoc#which-modules-are-re-layered[Which modules are re-layered], xref:reference.adoc#system-properties[System properties].
* **In a Vauban layer, no load-time agent** — when the loader defines the application's classes, it weaves `ProxyLink` at definition and `LoadTimeWeaving` stands down: no dynamic agent, and none of the JDK warning that comes with it. It also weaves the produced types whose proxies it places, and the superclasses they need, so a placed proxy does not chain a third-party constructor. xref:internals.adoc#weaving-tiers[weaving tiers].
* **The hello world shows the launcher form** — "Build and run" gives the launcher command next to the plain `java --module-path … --module …`. `Main` is unchanged; what changes is that the application starts inside a layer. xref:getting-started.adoc#build-and-run[Getting started — build and run].
* **A layer class knows its archive** — the classes the layer's loader defines, placed proxies included, now carry their archive as their code source, as on the module path. The location used to be `null`, so code that finds where a class comes from failed inside the layer: Foy skipped the jar of a `ServletContainerInitializer` and called it with no `@HandlesTypes` classes (vauban#153). xref:se.adoc#code-source[Where a layer class comes from].
* **Multi-release jars in the layer** — the layer's loader now reads a multi-release jar as the module path does: the `META-INF/versions/N/` entries win for the running JDK, so a library such as Jackson defines its versioned classes. The base version always won before (vauban#154). xref:se.adoc#multi-release[Multi-release jars].
* **The layer works from a `jlink` image** — inside a runtime image every module is served from `jrt:`, and the launcher used to find nothing to re-layer there and refuse to start, with a message about `--add-modules` that named the wrong cause. It now re-layers those modules as it does a module path, so placed proxies, encrypted archives and load-time weaving work in a `jlink` or `jpackage` image too. xref:se.adoc#limits[Vauban in Java SE — limits].
* **Kept roots in the re-layer policy** — `VaubanLayerFactory.applicationPaths` takes the root modules of a runtime and keeps their whole closure in the parent layer, whatever their names; every other explicit module that the name rules do not keep moves to the application layer. A runtime can name its roots, and the Vidocq runtime will (vidocq#247). The three-argument form is unchanged (vauban#154). xref:se.adoc#kept-roots[Kept roots].
* [.tag-new]#NEW# **`VaubanClassLoader.excludesPackage` is public** — a launcher or a build tool applies the loader's own rule for the packages it refuses to define (`javax.*`, `sun.*`, the container's own), instead of copying it (vauban#154).

== Client proxies without `opens`

Client proxies for third-party produced types, without `opens` (vauban#42) — the https://github.com/jakartaee/cdi/issues/1015[jakartaee/cdi#1015^] case, runnable as `example-cdi1015-lib` + `example-cdi1015-app`:

* **One strategy per case** — Internals carries the full decision table for where a `_ClientProxy` is generated and what it costs, resolved in order, first match winning, down to the shapes CDI 4.1 §3.10 makes unproxyable anywhere. xref:internals.adoc#proxy-strategies[client-proxy strategies].
* **Placed in-package proxies under a Vauban loader** — when a produced type has a package-private or protected overridable member, or no accessible constructor, its proxy must live in the type's own package. The processor ships that proxy as bytecode in the bean archive and the loader defines it into the library's package on a `findClass` miss: **zero `opens`, no agent, no rewritten jar**, the library used as shipped, signature intact. The third-party constructors do not run for the proxy (vauban#24); when a superclass the loader does not define blocks that, a WARNING says so. The library must still export the package. xref:internals.adoc#proxy-strategies[client-proxy strategies], xref:se.adoc#what-the-build-ships[what the build ships].
* **Fully-public eligibility walks the whole superclass hierarchy** — up to but excluding `java.lang.Object`. A method inherited from a superclass is neither declared by the produced type nor overridden by the proxy, so judging declared methods alone handed out a proxy that silently ran the superclass body against its own empty state. xref:internals.adoc#proxy-strategies[client-proxy strategies].
* **Which proxy do I get, and what do I have to do?** — a table in Usage maps each situation to what Vauban does and what is asked of you, from "nothing" for an ordinary bean to "start through the launcher" for a produced class whose proxy must be placed. A "What failure looks like" subsection quotes the three diagnostics verbatim. xref:usage.adoc#which-proxy[Which proxy do I get].
* **Boot-time opens are opt-in** — `-Dvauban.opens.auto=true` (vauban#42, Stage 3b) opens a listed produced type's package to `io.vidocq.vauban.core` at boot, through the weaving agent, and only when the package is not already open. It is **off by default**: opening another module's package behind the user's back is what this project faults runtime CDI implementations for needing. Left off, the container refuses and logs every way to avoid it. xref:internals.adoc#proxy-strategies[client-proxy strategies], xref:reference.adoc#system-properties[System properties].

== Build tooling and switches

* **`scanUnprocessedBeanArchives(onArchive)`** — a builder method that scans the `beans.xml` archives no Vauban build step indexed, and only those, so that a runtime reading the build-time indexes with `scanClasspath()` still finds the beans of a dependency compiled without the processor, without registering any bean twice. It reports each archive it scans. xref:getting-started.adoc#scan-unprocessed[Bootstrap modes].

* **`vauban:modularize`** — bound to `prepare-package`, **opt-in**: it gives the non-modular dependency jars of the closure a `module-info` of their own, written into `target/vauban-modularized/` under the original file name. `requires` comes from the types each jar uses, every package is exported, `META-INF/services` becomes `provides`, and the `ServiceLoader` lookups found in the bytecode become `uses`. It fails on a split package between two automatic jars and leaves automatic any jar whose own lookup cannot be declared legally, with the reason in `report.txt`. The copies never leave `target/`. It used to be `vidocq:modularize`. xref:reference.adoc#modularize[`vauban:modularize` in detail].
* **`vauban:enhance-dependencies`, and a copy that declares itself** — bound to `package`, **opt-in** and a *last resort*: an enhanced copy of a dependency jar carrying the co-located proxy, for when the shipped in-package proxy cannot work — no Vauban layer at runtime, a library that exports nothing, or a native image. The copy declares what it is: it drops the inherited signature files and per-entry digests rather than carrying a signature over content that no longer matches, and records `Vauban-Enhanced-From`, `Vauban-Enhanced-Digest` and `Vauban-Enhanced-By`. Those copies are not the artefact their coordinates name, and declaring them to SBOM and attestation tooling is the governance cost that keeps the goal opt-in. xref:reference.adoc#maven-plugin-goals[Maven plugin goals], xref:internals.adoc#proxy-strategies[client-proxy strategies].
* **`vauban:generate` pre-generates every intercepted subclass the container needs** — it used to write `<Bean>$$Intercepted` only for a bean with a class-level binding. It now writes one for every bean the container would wrap: a method-level binding (declared, inherited, or on an interface default method), a constructor binding, or an `@AroundInvoke` method of the bean's own. It lists them in its `_VaubanComponents`, which it did not, and writes none for an `@Interceptor` class. A module the plugin built, with such a bean, used to fail on the strict module path without an `opens` with `Could not define interceptor subclass`; it now boots (vauban#121). xref:reference.adoc#maven-plugin-goals[Maven plugin goals].
* **Reproducible generated output** — the processor and `vauban:generate` write the same files for the same input from one build to the next: provider entries and generated methods come out in a stable order, where the order used to depend on hash iteration and on what the JVM had loaded before. xref:internals.adoc#reproducible-output[Code generation].
* **`-Avauban.providesHint=false`** [.tag-new]#NEW# — the note on a generated `_VaubanComponents` no longer tells the module to declare it with `provides`, for a runtime such as Vidocq that declares it when it loads the module; the advice had every Vidocq build tell the user to edit a `module-info.java` that needed nothing (VAU-APT-004, Vidocq/vidocq#336). xref:reference.adoc#annotation-processor-options[Annotation-processor options].
* **`-Avauban.producerProxy=error|warn|note`** — the severity of the diagnostic emitted when a normal-scoped `@Produces` returns a class type that is not build-time proxyable across a module boundary, which leaves the runtime to fall back to a reflective proxy and an `opens`. Default `note`; `error` enforces zero fallback. xref:reference.adoc#annotation-processor-options[Annotation-processor options].
* **`-Dvauban.annotations.reflection=allow|warn|forbid`** — what the container may do when an annotation reaches it as an object rather than as index data. Matching and injection never reflect; four other things can, and this switch governs all four. Set `forbid` in a test to prove a deployment needs no reflection, or `warn` to see what a native image would need metadata for. A module compiled with the Vauban APT needs none of them, and it also carries a literal for each **public** qualifier or interceptor binding it uses from a dependency built without the processor, so `forbid` holds for those too. xref:reference.adoc#system-properties[System properties], xref:internals.adoc#aot[AOT compatibility].

== Interception of inherited and default methods

Interceptors now reach the methods a bean inherits, interface default methods included, and a bean that cannot be intercepted is told why. Several of these change what an existing application does:

* **Bindings on interface default methods apply** — an interceptor binding on an interface default method the bean does not override now selects its interceptor, by the rule that already held for a superclass method: the binding stops applying once a class of the bean overrides the method. The class-level bindings of an interface still never apply. A bean whose only binding sits on such a method is now intercepted, so it must be proxyable: a `final` bean class, or a bean with a `final` method, bound only through a default method used to deploy un-intercepted and now fails with a `DeploymentException`. xref:internals.adoc#intercepted-methods[Which methods the intercepted subclass covers], xref:internals.adoc#unproxyable-intercepted[unproxyable intercepted beans].
* **Inherited `protected` and package-private methods are intercepted at run time** — the `$$Intercepted` subclass the container generates when none was pre-generated, and the one `vauban:generate` writes, now override the protected and package-private methods the bean inherits, as the processor's subclass already did. A call the bean makes on itself to such a method now runs its interceptors too. xref:internals.adoc#intercepted-methods[Which methods the intercepted subclass covers].
* **Client proxies forward default methods, and reach a shadowed one through its interface** — a normal-scoped bean's client proxy, the processor's and the run-time one, now forwards the interface default methods the bean does not override to the contextual instance, where the default body used to run on the proxy instance, with no interceptor. A default method that a superclass method the bean does not inherit (a private one, say) hides from the JVM is now called through its interface by the generated subclass and proxies, when that interface can be named, where the call used to fail with `IllegalAccessError` or `AbstractMethodError`. xref:internals.adoc#intercepted-methods[Which methods the intercepted subclass covers].
* **`getMethod()` and `getInterceptorBindings()` see the inherited declaration** — for a method the bean inherits, `InvocationContext.getMethod()` now returns the superclass method or the interface default method the call runs instead of the generated `$$super$` bridge, and `getInterceptorBindings()` now includes the method-level bindings of that declaration. An interceptor that reads either one sees more than before for inherited and default methods. xref:internals.adoc#intercepted-methods[Which methods the intercepted subclass covers].
* **An unproxyable intercepted bean is a deployment problem, with its reason** — the check the container makes when it wraps an intercepted bean (one the deployment validation has not already rejected) now throws a `DeploymentException` for a `final` class too, where it threw a `DefinitionException`, and each of its three messages (final class, final method, only a private no-arg constructor) ends with why the bean is intercepted: the binding, and the declaration that carries it. Code or tests that expected the former exception type or texts need updating. xref:internals.adoc#unproxyable-intercepted[unproxyable intercepted beans].
* **What Java source cannot override is emitted as bytecode** — a bean that inherits a member whose signature names a type its package cannot name (a package-private type of another package, a private nested type) used to break the build: the processor wrote an override Java source cannot express. It now emits that intercepted subclass or client proxy, a producer's included, as bytecode, which overrides and forwards by descriptor, and the module's source `_VaubanComponents` reaches it through its own lookup, with no `opens` (vauban#120, BUG-20261004-09). A method whose return type the subclass may not access is left out of the subclass and runs un-intercepted, where the run-time subclass used to throw `IllegalAccessError` on every call. xref:internals.adoc#intercepted-methods[Which methods the intercepted subclass covers].
* **New processor warnings** — when a shadowed default method cannot be reached through a nameable interface, the processor's client proxy and intercepted subclass leave it out, and when a method's return type cannot be accessed, the intercepted subclass leaves it out. The processor says so in a compiler warning: `[Vauban] <bean>: the client proxy does not forward the inherited default method …` (`the producer's client proxy`, on the producer method, for a producer), or `[Vauban] <bean>: the generated subclass does not intercept …`, each with the reason and what a call does instead. xref:internals.adoc#intercepted-methods[Which methods the intercepted subclass covers].
* **Every processor client proxy forwards inherited methods** — a normal-scoped bean with private constructors only, or a top-level class whose own name contains `$`, got a proxy built from the index that forwarded only the methods the bean class declares, so a superclass method or a default method ran on the proxy instance. Such a bean now gets a proxy that forwards them like any other. A type whose own name contains `$` is also named correctly in the intercepted subclass, the producers' proxies and the annotation artefacts, which did not compile, and a normal-scoped producer of a nested class or interface now gets a build-time proxy (vauban#122). xref:internals.adoc#intercepted-methods[Which methods the intercepted subclass covers].
* **Intercepted beans with an `@Inject` constructor under `forbid`** — such a bean read its constructor parameters' qualifiers by reflection and could not be created under `-Dvauban.annotations.reflection=forbid`. It now takes them from its descriptor (BUG-20261007-03). xref:internals.adoc#intercepted-methods[Which methods the intercepted subclass covers].
* **Lifecycle callbacks are not business methods** — an `@AroundInvoke` interceptor no longer runs around a bean's `@PostConstruct` and `@PreDestroy` callbacks (VAU-INT-006, vauban#114). Those callbacks reach only the interceptors' own lifecycle methods, where `InvocationContext.getMethod()` is `null`, as Jakarta Interceptors 2.2 requires. With a class-level binding such as `@Transactional`, `@Retry` or `@Timed`, the interceptor used to wrap `init()` and `dispose()` as if they were business calls: a transaction around the callback, a metric or a log line named after it. Neither happens any more. The processor's intercepted subclass and the one the container generates use the same list of methods to leave out: `@Inject` initializers, the target class's interceptor methods, and the lifecycle callbacks. xref:internals.adoc#intercepted-methods[Which methods the intercepted subclass covers].
* **Recompile with the matching processor** — the classes the processor generated live in your archive, so an archive compiled by an earlier processor keeps them until it is recompiled: its client proxies forward no default method, and a bean bound only through an interface default method has no pre-generated `$$Intercepted` subclass. The container now intercepts that bean and generates the subclass itself. On the class path that works; on the module path, with the bean's package not opened to `io.vidocq.vauban.core`, the deployment fails with `DeploymentException: Could not define interceptor subclass`, where the earlier container left the bean un-intercepted. Recompiling with this release's processor fixes it, and also fixes a bean bound only through a superclass method, which failed the same way before. xref:internals.adoc#intercepted-methods[Which methods the intercepted subclass covers].

== Naming

* **The JNDI `java:` namespace with `vauban-naming`** — a new module answers `new InitialContext().lookup("java:comp/env/jdbc/orders")` from the running container, so code written for an application server finds its resources (Vidocq/vidocq#297). `JndiBindings` beans declare each name, bound to a bean (a type and its qualifiers, also written as text: `javax.sql.DataSource @Named("orders")`) or linked to another name, in four distinct namespaces (`java:comp`, `java:module`, `java:app`, `java:global`); the declarations are checked when the container starts. Its contexts hold no container and follow a restart; the namespace is read-only; names not known in advance come from `JndiNameProvider` beans. `JavaNaming.installAsDefault` makes it the JVM default unless the application chose a factory, and LDAP or RMI names still go to the JDK. xref:jndi.adoc[The JNDI java: namespace].

== Web contexts

* **`@SessionScoped` with `vauban-webcontexts`** — a new module provides the session context CDI Lite leaves to the servlet container: one instance per session, kept in the session's attributes, destroyed with the session between `@BeforeDestroyed` and `@Destroyed(SessionScoped.class)`. Foy drives it through `foy-cdi-vauban`; another web container drives it through `WebContexts`. It used to fail with `ContextNotActiveException: No context registered for scope jakarta.enterprise.context.SessionScoped` (Vidocq/foy#21). xref:usage.adoc#web-contexts[Web contexts].
* **`RequestContextController` and `@ActivateRequestContext`** — the two CDI Lite ways to activate the request context outside a request were missing: the built-in `@Dependent` controller and the built-in interceptor (priority `PLATFORM_BEFORE + 100`). Foy activates the request context through the controller, so under Vauban a `@RequestScoped` bean used from a servlet failed with `ContextNotActiveException: RequestScope is not active`; it now gets one instance per request (vauban#147). xref:usage.adoc#activating-the-request-context[Activating the request context].
* **The request context is per thread, with its events** — activated outside Cassini's scope, the request context kept its state in a field every thread shared, so two concurrent activations overwrote each other's instances; each thread now has its own. Activating and deactivating it fires `@Initialized`, `@BeforeDestroyed` and `@Destroyed(RequestScoped.class)`, which Vauban never fired, Cassini's requests included (vauban#147). xref:usage.adoc#activating-the-request-context[Activating the request context].

== Extensions

* **Module lookups for trusted extensions** — `ModuleLookups.lookupFor(Class<?>)` gives an extension a full-privilege lookup on a class the container manages. The lookup is supplied by the generated `_VaubanComponents` of the class's package, whether the processor or the Maven plugin wrote it, so a `private` member such as a MicroProfile Fault Tolerance `fallbackMethod` is reachable with no `opens`. The package is exported only to the extension modules named in `io.vidocq.vauban.core`, and a provider hands its lookup only to the container. xref:internals.adoc#module-lookups[Module lookups for trusted extensions].
* **An extension can tell build time from container start** — `ExtensionPhase.isBuildTime()` is `true` while the annotation processor or the Maven plugin runs a build compatible extension and `false` when the container does, so an extension that checks the deployment's environment can leave that check to the container start (ravel#21). xref:concepts.adoc#extension-phase[Build time or container start].
* **Synthetic beans stay out of the bean list** — an application whose extension synthesised a bean in the processor failed to boot with a `NullPointerException`: the bean list named the synthetic bean's type as if it were a managed class (ravel#21). xref:concepts.adoc#build-compatible-extensions[Build Compatible Extensions].
* **A synthetic bean's language-model types survive build time** — a type an extension gives the processor as a language-model type, `addBean(...).type(types.ofClass(info))` for a class the compilation is still producing, was validated at build time but dropped from the metadata the runtime reads: the bean was typed `Object` alone at run time and its injection points were unsatisfied. Class types are now written by name and loaded at run time; parameterized language-model types still are not (vauban#127, BUG-20261008-01). xref:concepts.adoc#build-compatible-extensions[Build Compatible Extensions].
* **Every synthetic param survives build time** — when the processor runs an extension, the params it gives a synthetic bean or observer reach the creator: arrays, `ClassInfo`, `Annotation`, `AnnotationInfo` and `InvokerInfo` used to be dropped without a word, `Class` and `Enum` params were lost at boot, and a synthetic observer got no param at all, so the creator read `null`. A param that cannot be recorded now fails the build, and one naming a class the boot cannot load fails the deployment (vauban#130, BUG-20261008-02). xref:concepts.adoc#build-compatible-extensions[Build Compatible Extensions].
* **`@Registration` sees what every `@Enhancement` did** — each phase now runs for every extension before the next phase starts, and `@Registration` gets the beans as `@Enhancement` left them, the classes it made beans included. An extension run by the processor used to miss a class it had made a bean itself (Foy's unscoped `@WebServlet`), and an extension's `@Registration` could run before another extension's `@Enhancement`. `BeanInfo.scope().name()` also no longer throws for a built-in scope at build time (vauban#131, BUG-20261008-03). xref:concepts.adoc#build-compatible-extensions[Build Compatible Extensions].
* **Stereotypes and custom scopes are bean-defining at build time** — the processor only looked at classes carrying one of a fixed list of annotations (`@ApplicationScoped`, `@RequestScoped`, `@Dependent`, `@Singleton`, `@Produces`, `@Interceptor`) and the extensions' triggers. A class whose only bean-defining annotation was an application stereotype, a custom scope, `@SessionScoped` or `@Model` was no bean. Any annotation meta-annotated `@Stereotype`, `@NormalScope` or `@Scope` now counts, whether it is declared in the same compilation or in a library (vauban#132, BUG-20261008-04). xref:concepts.adoc#bean[Bean].
* **Annotations an `@Enhancement` adds keep their members** — `ClassConfig.addAnnotation(NamedLiteral.of("x"))` named the bean with its default name, and a qualifier added with members, to a class or a field, lost them, so an injection point that told two beans apart by a member was unsatisfied. The build-time patch now records members, the container applies them, and a nested class's default name no longer keeps its `Outer$` prefix on that path. A patch written by an earlier build still reads, without members (vauban#135, BUG-20261008-05). xref:concepts.adoc#build-compatible-extensions[Build Compatible Extensions].
* **Which generator covers what** — a generated provider declares what it runs in-module (`VaubanComponentProvider.coverage()`), and `VaubanContainer.codegenCoverage()` tells, per bean, observer and interceptor, which generator covers each operation and which falls back to reflection. The Vidocq dev console shows it. A provider generated before this answers `null`. xref:internals.adoc#code-generation-via-class-file-api-and-apt[Code generation].

== Fixes that change behaviour

* [.tag-new]#NEW# **A lifecycle observer that throws fails the boot, with a log** — an exception from an observer of `@Initialized(ApplicationScoped.class)` or `Startup` was discarded, and the application started half-initialized with nothing in the log. `build()` now throws a `DeploymentException` naming the observer, `VaubanContainer.current()` stays `null`, and a `WARNING` line gives the stack trace. At shutdown the exception is logged and `close()` completes. With `vauban.annotations.reflection=forbid`, the observers of these events are notified at last: computing their qualifier's key needed reflection, and that failure was swallowed with the rest (vauban#97). **When upgrading**, an application whose startup observer throws no longer starts. xref:usage.adoc#lifecycle-observer-failures[When a lifecycle observer throws].
* [.tag-new]#NEW# **A broken extension service entry no longer fails the compilation** — a `META-INF/services/jakarta.enterprise.inject.build.compatible.spi.BuildCompatibleExtension` entry on the annotation processor path naming a class that cannot be loaded or instantiated failed the compilation with a `ServiceConfigurationError`. The processor now skips that provider with a warning naming the service file and the provider, and runs the other extensions (vauban#199, Vidocq/vidocq#285). xref:concepts.adoc#broken-extension-entry[Build Compatible Extensions].
* [.tag-new]#NEW# **A bean in the test sources no longer hides the main beans** — the test compilation emitted a second `_VaubanComponents` and `vauban-beans.list`, which hid the main ones when the tests ran: the main beans went missing, and Vidocq's mansart example could not inject `ProductRepository` from a test bean. The test compilation now emits `_VaubanComponentsTests`, found through the main provider, and merges the main indexes into its own (vauban#101). xref:usage.adoc#test-sources-beans[Beans in the test sources].
* [.tag-new]#NEW# **An `@AroundConstruct` that proceeds works on the fallback interception path** — when the container cannot define a bean's `$$Intercepted` subclass the regular way and falls back on a second definition, a bean bound to an `@AroundConstruct` interceptor that calls `proceed()` failed to be created with a `NullPointerException`. It is now created through its interceptor chain as on the regular path, and `proceed()` returns the instance the container hands out (VAU-INT-007, Vidocq/vidocq#285). xref:internals.adoc#intercepted-methods[Which methods the intercepted subclass covers].
* [.tag-new]#NEW# **`@VaubanTest` injects a `@TestInstance(PER_CLASS)` test** — with the per-class lifecycle, JUnit creates the test instance before the extension started the container, so its `@Inject` fields stayed `null`. The extension now starts the container when it injects the instance, if it is not started yet; the class still gets a single container (VAU-TEST-002, vauban#190). xref:reference.adoc#junit-lifecycles[Test instance lifecycles].
* [.tag-new]#NEW# **A stereotype declaring `@Named("…")` fails the boot even when no bean carries it** — the index validation skipped annotation types, so its check that a stereotype declares an empty `@Named` only never ran, and the error came only through a bean that carried the stereotype. A stereotype the container indexes (handed to `addBeanClasses`, or added by an extension) is now rejected with a `DefinitionException` on its own, as CDI 4.1 (2.8.1.3) requires (vauban#191, Vidocq/vidocq#285). xref:internals.adoc#boot-failures[Failures are reported, not swallowed].
* [.tag-new]#NEW# **A constructor an `@Enhancement` marks `@Inject` is the bean constructor** — a bean that also declared a no-arg constructor was still created through it, so what the injected constructor sets stayed `null`, and the constructor's parameters were missing from the bean's injection points. The container now creates the bean through the constructor the enhancement marked, with the exact overload when several take as many parameters, and validates and reports its parameters like those of a constructor the class marks itself (VAU-BCE-006, Vidocq/vidocq#285). **When upgrading**, a parameter of such a constructor that no bean satisfies now fails the deployment. xref:concepts.adoc#build-compatible-extensions[Build Compatible Extensions].
* [.tag-new]#NEW# **A build compatible extension sees the type parameters of a generic class** — `ClassInfo.typeParameters()` always returned an empty list, in `@Enhancement`, `@Registration` and every other phase, so an extension could neither read the type parameters of a class nor get a type variable from it. It now returns them in declaration order, each with its bounds (`java.lang.Object` when none is declared), read from the class signature in the index, in the processor as at container start (VAU-BCE-007, vauban#207, Vidocq/vidocq#285). xref:concepts.adoc#build-compatible-extensions[Build Compatible Extensions].

* [.tag-new]#NEW# **A broken extension service entry no longer fails `vauban:generate`** — a `META-INF/services/jakarta.enterprise.inject.build.compatible.spi.BuildCompatibleExtension` entry naming a class that cannot be loaded or instantiated failed the goal with a `ServiceConfigurationError`. The goal now skips that provider with a warning naming the service file and the provider, and runs the other extensions (vauban#189, Vidocq/vidocq#285). xref:reference.adoc#maven-plugin-goals[Maven plugin goals].
* [.tag-new]#NEW# **An intercepted bean's factory works without a creational context** — `ManagedBean.factory().create()` on a bean bound to an `@AroundConstruct` interceptor, called with no creational context, failed with a `NullPointerException`, on the regular interception path as on the fallback one. The factory now gives the bean a creational context of its own: the bean is created through its interceptor chain, and one interceptor instance serves its construction and its methods (vauban#192, Vidocq/vidocq#285). xref:internals.adoc#intercepted-methods[Which methods the intercepted subclass covers].
* [.tag-new]#NEW# **`Bean#create(null)` works on a bean bound to a `@PostConstruct` interceptor** — `Bean#create` called with no creational context on such a bean failed with a `NullPointerException` in its `@PostConstruct` step. The bean now gets a creational context of its own: its `@PostConstruct` runs through its interceptors, and one interceptor instance serves its construction, its `@PostConstruct` and its methods (vauban#200, Vidocq/vidocq#285). xref:internals.adoc#intercepted-methods[Which methods the intercepted subclass covers].
* [.tag-new]#NEW# **`Bean#destroy(instance, null)` runs the `@PreDestroy` callbacks of an intercepted bean** — `Bean#destroy` called with no creational context on a bean bound to a `@PreDestroy` interceptor returned without error, but skipped both the interceptor's and the bean's `@PreDestroy` methods. The bean now gets a creational context of its own for its destruction: its `@PreDestroy` runs through its interceptors, which are then released. An exception from a `@PreDestroy` callback is still caught by `destroy()`, as CDI requires (vauban#203, Vidocq/vidocq#285). xref:internals.adoc#intercepted-methods[Which methods the intercepted subclass covers].
* [.tag-new]#NEW# **Synthetic observers of wildcard-parameterized and array types** — `addObserver(types.parameterized(List.class, types.wildcardWithUpperBound(...)))`, or an observer of an array type, failed the `@Synthesis` method with _Unsupported type for synthetic observer_, while CDI lets any type be observed. Such an observer is now registered when the container runs the extension, and receives the events of the types it observes: an observer of `List<? extends Number>` gets a `List<Integer>`, not a `List<String>`. When the processor runs the extension, a wildcard, a generic array or a type variable in the observed type fails the build with a message naming the observer, since the recorded metadata cannot carry such a type (VAU-OBS-003, vauban#188). xref:concepts.adoc#build-compatible-extensions[Build Compatible Extensions].
* [.tag-new]#NEW# **Synthetic observers of wildcard-parameterized and array types** — `addObserver(types.parameterized(List.class, types.wildcardWithUpperBound(...)))`, or an observer of an array type, failed the `@Synthesis` method with _Unsupported type for synthetic observer_, while CDI lets any type be observed. Such an observer is now registered when the container runs the extension, and receives the events of the types it observes: an observer of `List<? extends Number>` gets a `List<Integer>`, not a `List<String>` (VAU-OBS-003, vauban#188). xref:concepts.adoc#build-compatible-extensions[Build Compatible Extensions].
* [.tag-new]#NEW# **A synthetic observer of a parameterized type recorded by the processor receives its events** — when the annotation processor ran the extension, an observer of `List<String>` was recorded by a name the boot could not load, and was dropped at boot without a word: the application started, and the observer never received an event. The metadata now records every observed type in a notation the boot reads back, wildcards, arrays and type variables included, and metadata written by the previous version reads the same. A recorded observed type the boot cannot read fails the deployment, naming the observer (VAU-OBS-005, vauban#206). xref:concepts.adoc#build-compatible-extensions[Build Compatible Extensions].
* [.tag-new]#NEW# **The processor records a synthetic observer of a class of the same build** — when the annotation processor ran an extension that added, in `@Synthesis`, an observer of a class the compilation was still producing (`addObserver(types.ofClass(info))`, or that class as a type argument), the build failed with _Cannot resolve type_: the observed class was loaded on the spot, before it existed. At build time the observed type is now recorded by name and loaded at boot, and the observer receives its events. When the container runs the extension, a type it cannot load still fails the `@Synthesis` method as before (VAU-APT-003, vauban#210). xref:concepts.adoc#build-compatible-extensions[Build Compatible Extensions].

* [.tag-new]#NEW# **`vauban:modularize` follows a `ServiceLoader` helper called through an interface** — Vaadin's `VaadinService` calls `Lookup.lookupAll(InstantiatorFactory.class)`, and `LookupImpl.lookupAll` passes the type to `ServiceLoader.load`. The call went unseen, so `flow.server` missed `uses InstantiatorFactory` and failed at boot once explicit. A method declared by a supertype now counts as a lookup when one of its implementations is one. This can reveal that a helper has no legal explicit form: `flow.server` would need a `uses` for types of modules that require it, and stays automatic (vauban#167). xref:reference.adoc#modularize[`vauban:modularize` in detail].

* [.tag-new]#NEW# **`vauban:modularize` lists resource-only directories as packages** — `jlink` refused a modularized jar holding resources in a directory without classes, such as Vaadin's `flow-server` (_descriptor indicates the set of packages is … but module contains packages …_). Such a directory is now a package of the module, unless another jar of the closure holds it too, which the build reports (vauban#163). xref:reference.adoc#resource-packages[`vauban:modularize` in detail].

* [.tag-new]#NEW# **`vauban:modularize` declares only the `provides` the module can read** — a service file for an optional dependency missing from the closure, such as `reactor-core`'s micrometer `ContextAccessor`, used to become a `provides` that rejected the whole graph at boot (_does not read a module that exports …_). It is now dropped with a warning, and a service type from another jar of the closure adds the `requires` it needs (vauban#162). xref:reference.adoc#provides-legality[`vauban:modularize` in detail].

* [.tag-new]#NEW# **`vauban:modularize` accepts a jar without classes** — a Maven aggregator jar such as `vaadin-core` gets an empty explicit module, which `jlink` accepts, where the goal used to fail with _it holds no class in any package_ (vauban#160). xref:reference.adoc#jar-without-classes[`vauban:modularize` in detail].

* [.tag-new]#NEW# **`vauban:modularize` declares `uses` for `load(Spi.class, getClass().getClassLoader())`** — a `ClassLoader` taken from a computed `Class` used to drop the service type from the scan, so the synthesized descriptor missed the `uses` and the jar failed at boot with _does not declare `uses`_. Vaadin's `flow-server` (`FeatureFlagProvider`) was the case (vauban#158). xref:reference.adoc#modularize[`vauban:modularize` in detail].

* **Bean methods that declare checked exceptions compile** — an observer such as `void onStart(@Observes @Initialized(ApplicationScoped.class) Object event) throws Exception`, a producer, an initializer or a constructor that declares a checked exception made the generated `_VaubanComponents` fail to compile with `unreported exception java.lang.Exception`. The generated code now rethrows it, and the exception reaches the container unwrapped (vauban#145). xref:internals.adoc#checked-exceptions[Code generation].
* **Intercepted beans in a package you do not export** — a bean with an interceptor (a `@Retry` method, for instance) in a package the module neither exports nor opens failed on first use with `IllegalAccessException: … does not export … to module io.vidocq.vauban.core`: the subclass was created in-module by the generated provider, but its wiring method was then called by reflection. That call now goes through the module lookup the provider grants, so nothing has to be exported (BUG-20261010-02). xref:internals.adoc#module-lookups[Module lookups].
* **A producer's disposer runs once** — `Bean#destroy` ran it twice (vauban#115). xref:usage.adoc#producers-and-disposes[Producers and `@Disposes`].
* **A disposer's other parameters are injection points** — qualifiers included: a qualified parameter used to fail validation as unsatisfied, or receive the `@Default` bean (vauban#89). xref:usage.adoc#producers-and-disposes[Producers and `@Disposes`].
* **Default `@Named` name of a nested bean class** — `Outer.ReportService` is now named `reportService`, no longer `outer$ReportService`. A lookup by the old name must be updated (vauban#116). xref:usage.adoc#qualifiers[Qualifiers].
* **Nested beans work on the module path** — a normal-scoped `static` nested bean now gets a source client proxy that its module's provider instantiates, where it used to be left out of the provider and fall back to reflection, which a module that opens nothing refuses. xref:usage.adoc#which-proxy[Which proxy do I get].
* **The generated provider uses the `@Inject` constructor** — when a bean has both an `@Inject` constructor and a no-arg one, the provider used to build it through the no-arg one only, so the container fell back to reflection and a named module without `opens` could not create the bean (grimm#15). xref:internals.adoc#code-generation-via-class-file-api-and-apt[Code generation].
* **Failures are reported, not swallowed** — a listed bean class that cannot be loaded is named in a warning instead of vanishing, a failed field injection reaches the caller instead of leaving the field `null`, and the build compatible extension phase resolves bean classes across every loader of the deployment, so CDI invokers no longer fall back to reflection under `vidocq:dev` (grimm#15, vauban#98). xref:internals.adoc#boot-failures[Failures are reported, not swallowed].
* **`beans.xml` discovery modes are honoured** — default SE discovery used to read every `META-INF/beans.xml` as `all`, so an `annotated` (or empty) `beans.xml` turned every concrete class of the archive into a bean, and a `none` one did not skip it. `annotated`, `all` and `none` now behave as the specification describes. xref:se.adoc#bean-archives[Default discovery: bean archives].
