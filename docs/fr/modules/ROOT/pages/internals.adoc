= Fonctionnement interne
:description: Codegen Class-File API, pipeline APT, modèle de threading, séquence de bootstrap.

[.lead]
Vauban repose sur un principe simple : tout ce qui peut être calculé à la compilation l'est. Aucune réflexion à chaud, aucun proxy dynamique, aucune librairie de bytecode externe. Cette page décrit les choix d'implémentation qui supportent cette discipline.

== Codegen via Class-File API et APT

CDI 4.1 décrit un modèle d'objets richement réflexif : `Bean<T>`, `BeanManager`, `InjectionPoint`, `AnnotatedType`. Vauban refuse d'évaluer ce modèle au runtime. Il le compile.

Deux outils interviennent à `process-classes` :

. **`vauban-indexer`** — parcourt le module-path à la compilation et produit un fichier d'index (`META-INF/vauban/index.bin`). L'équivalent statique du `BeanArchive` runtime de Weld. Zéro dépendance.
. **`vauban-processor`** — `javax.annotation.processing.Processor` qui consomme l'index et émet du bytecode via la **Class-File API** (https://openjdk.org/jeps/484[JEP 484]). Pas d'ASM, pas de Byte Buddy, pas de Gizmo.

Pour chaque bean, le processeur génère :

[cols="1,3"]
|===
| Artefact généré | Rôle

| `MyBean$$_Factory`
| Implémente `BeanFactory<MyBean>`. Constructeur sans argument. Appelle le constructeur cible avec les dépendances déjà résolues, puis exécute `@PostConstruct`.

| `MyBean$$_ClientProxy`
| Sous-classe générée pour les scopes normaux. Intercepte chaque méthode publique et délègue au contexte actif via `Context.get(bean, ctx)`.

| `MyProducer$$_ProducerFactory`
| Pour chaque méthode `@Produces`, encapsule la création et la destruction (`@Disposes`).

| `MyObserver$$_ObserverMethod`
| Pour chaque méthode `@Observes`, fournit `notify(event)` sans réflexion.
|===

[NOTE]
====
Le drift entre `ClientProxyGenerator` (compile-time) et `RuntimeClientProxyGenerator` (fallback) est un risque tracé dans link:{repo-vauban}/src/branch/main/BUG.md[BUG.md] (entrée VAU-PRX-002). Toute évolution d'un générateur doit être répliquée dans l'autre.
====

== Pipeline APT — diagramme de séquence

[plantuml]
....
@startuml
skinparam shadowing false
participant "javac" as JC
participant "vauban-indexer" as IDX
participant "vauban-processor" as PROC
participant "Class-File API" as CFA
participant "filer" as F

JC -> IDX : annotation discovery
IDX -> IDX : scan module-path\n+ classpath
IDX -> PROC : VaubanIndex\n(beans, scopes, qualifiers)
PROC -> PROC : BeanDiscovery\n+ DeploymentValidator
PROC -> PROC : BceProcessor\n(Build Compatible Extensions)
PROC -> CFA : ClassBuilder\nper bean
CFA -> F : write _Factory.class
CFA -> F : write _ClientProxy.class
CFA -> F : write _ProducerFactory.class
F -> JC : generated-sources\n+ generated-classes
@enduml
....

Tout l'index, toute la grille d'injection, tous les proxies sont écrits avant que `javac` ne finisse son travail.

[#weaving-tiers]
== Étages de tissage du client proxy

Un bean normal-scoped sans constructeur no-arg non privé a besoin d'une porte d'entrée
sans effet de bord pour son client proxy : le constructeur synthétique
`protected <init>(ProxyLink)` (xref:usage.adoc[Usage — beans proxyables]). Le traitement
d'annotations ne peut pas ajouter de membre à une classe existante (JSR 269 ne crée que de
nouveaux fichiers), le marqueur est donc *tissé dans les octets compilés* par les
transformations Class-File API du module `vauban-weaver` — une implémentation canonique
unique, appliquée à trois moments possibles :

[cols="1,2,2"]
|===
|Étage |Quand |Couvre

|Plugin javac
|Événement `COMPILATION finished`, auto-démarré (`Plugin.autoStart()`) depuis le jar du
processeur d'annotations ; le processeur publie un plan de tissage, le plugin patche les
fichiers de classes que javac vient d'écrire
|Maven, Gradle, `javac` nu, tout build basé sur javac — sans configuration

|`vauban-maven-plugin`
|`process-classes`
|Ceinture et bretelles pour les builds Maven ; jars de l'écosystème dont les classes ne
passent pas par javac (enrichissement, packaging sjar)

|Agent au chargement
|Démarrage du container — `LoadTimeWeaving` détecte les beans normal-scoped non tissés
dans l'index *avant tout chargement de classe de bean* (octets des ressources
uniquement), puis attache dynamiquement `vauban-weaver-agent.jar` (embarqué dans
`vauban-core`) et lui remet un plan de tissage explicite ; le `ClassFileTransformer`
applique la même transformation à la définition de la classe
|Builds d'IDE — le compilateur d'IntelliJ (JPS) écrit les classes rédigées à la main sur
disque *après* la fin de javac, les deux étages de build voient donc des fichiers périmés
|===

Ce qu'il faut savoir sur l'étage au chargement :

* **Pourquoi un agent et pas de la réflexion** — les modules applicatifs Vidocq gardent
  les packages de beans totalement encapsulés (zéro `opens`, zéro `exports`). Toute
  astuce d'instanciation réflexive (construction « relaxed » façon `ReflectionFactory`)
  est bloquée par Java Modules ; un `ClassFileTransformer` travaille sous le contrôle
  d'accès et produit un bytecode identique à un build tissé.
* **Auto-attachement via un processus enfant** — la JVM refuse `VirtualMachine.attach()`
  sur elle-même ; `LoadTimeWeaving` lance
  `java -cp vauban-weaver.jar io.vidocq.vauban.weaver.AttachBack <pid> <jar> <plan>`,
  qui s'attache en retour au parent et charge l'agent. La session de débogage de l'IDE
  n'est pas affectée. Le JDK affiche son avertissement standard sur les agents
  dynamiques.
* **Piloté par plan, sans heuristique** — l'agent ne touche que les classes nommées dans
  le plan calculé depuis l'index du container : les beans non tissés reçoivent le
  constructeur marqueur, leurs compagnons `_ClientProxy` sont reciblés dessus.
* **Contrainte d'ordre** — ajouter un constructeur n'est pas une retransformation valide,
  une classe chargée avant l'attachement ne peut donc plus être tissée. Le point
  d'ancrage s'exécute dans `VaubanContainerBuilder.build()` juste après la finalisation
  de l'index et avant la découverte des beans, et la détection elle-même ne charge
  aucune classe.
* **Désactivation** — `-Dvauban.weaving.loadtime=disabled` ; les beans non tissés
  échouent alors à la validation de déploiement avec le diagnostic vauban#24 habituel.
  Le mode explicite `-javaagent:vauban-weaver.jar=<plan>` est aussi supporté
  (`Premain-Class`).

== Chargement de classes

Vauban possède le chargement des classes applicatives, sous forme d'un moteur unique avec
deux natures de plugins chaînées avant `defineClass` :

....
             ┌─ sources ─────────────┐   ┌─ transformers ───────────┐
archive ───▶ │ dir | jar | sjar | …  │ ─▶│ cdi-proxifier | (futur)  │ ─▶ defineClass
             └───────────────────────┘   └──────────────────────────┘
....

* `vauban-classloader-spi` — les contrats : `ByteSourcePlugin` (*d'où viennent les octets
  d'une archive* — le support des jars chiffrés dans `vauban-sjar` en est un plugin) et
  `ClassTransformerPlugin` (*ce qui arrive aux octets* avant définition — SPI
  expérimentale). Les deux sont découverts par ServiceLoader et ordonnés par priorité.
* `vauban-classloader` — le moteur : `VaubanClassLoader` résout chaque archive via le
  premier plugin source qui la prend en charge (jars simples et répertoires éclatés
  intégrés) et fait passer chaque classe par la chaîne de transformers. Le transformer
  `cdi-proxifier` livré applique le tissage vauban#24 (`ProxyLinkWeaver`, mêmes octets
  qu'un tissage au build — idempotent) à la définition ; un bean non tissé dans une
  archive *chiffrée* ne peut être corrigé nulle part ailleurs, la composition
  déchiffrement → tissage découle gratuitement du chaînage. Le scanner du container
  définit les classes sjar à travers ce moteur. Diagnostics : transformations loguées,
  `-Dvauban.classloader.dump=<dir>` écrit les octets transformés,
  `-Dvauban.classloader.transformers.disabled=<noms>` désactive des transformers par
  nom, et un échec de transformer fait échouer le chargement — rien de silencieux.
* `VaubanLayerFactory` — le volet module path : les archives applicatives restent *hors*
  du module path de la JVM et se résolvent dans une `ModuleLayer` enfant dont l'unique
  loader est le moteur. Exports et opens restent appliqués dans la layer enfant ;
  `ServiceLoader` (provides/uses) fonctionne à travers elle. Le lanceur Vidocq active ce
  mode avec `-Dvidocq.app.path=<archives>` (`VidocqAppLayer`, installé avant que quoi que
  ce soit ne touche une classe applicative), et tous les véhicules de lancement Vidocq
  l'utilisent par défaut : les distributions packagées embarquent le jar applicatif dans
  `app/` (les scripts démarrent le runtime, opt-out `vidocq.package.layer=false`),
  `vidocq dev` transmet `target/classes` de la même façon (opt-out
  `vidocq.dev.layer=false`), et les embarqueurs in-process (le CLI) obtiennent la layer
  via `VidocqBootstrap.configure()`. Un `main` applicatif s'exécute à travers la layer
  via `-Dvidocq.app.main` — son package est exporté vers le runtime par le
  `ModuleLayer.Controller` de la layer, la même technique que le lanceur du JDK.
  L'agent de tissage au chargement s'efface alors — le loader tisse, sans
  `java.lang.instrument` et sans l'avertissement JDK sur les agents dynamiques. Note
  d'implémentation pour les loaders de layer custom : la JVM charge les classes des
  modules de layer via `findClass(String moduleName, String name)`, dont
  l'implémentation héritée retourne `null` — les deux chemins (par nom et par module)
  sont surchargés. Limitation connue : les handlers JUL déclarés dans
  `logging.properties` doivent vivre sur le module path — `LogManager` les instancie via
  le system class loader, qui ne voit pas la layer.
* Le container lui-même ne réfléchit jamais dans les packages applicatifs : les providers
  générés `_VaubanComponents` (`ServiceLoader`) instancient beans et proxies in-module,
  ce qui rend possibles les déploiements sans `opens`.

La layer est aussi ce qui rend possible le **hot reload in-JVM** du mode dev (M3) :
après une recompilation réussie, `vidocq dev` signale la JVM en cours (touch d'un
fichier de reload, `vidocq.dev.hotReload=false` restaure le cycle respawn) — le runtime
arrête le déploiement, jette la layer applicative et son loader, résout une layer neuve
sur les classes recompilées et redémarre. Même processus, JIT chaud, debugger et dev
services intacts. Les hôtes qui hébergent Cassini à travers de tels reloads doivent
purger ses caches statiques de découverte
(`io.vidocq.cassini.runtime.CassiniMaintenance.resetDiscoveryCaches()`, appelé par le
`onStop` de l'extension Cassini de Vidocq) : ils sont indexés par des objets `Class`
applicatifs, qu'une nouvelle layer remplace en bloc.

Étude de conception et jalons : `tasks/vauban-classloader-universal.md` (M1 moteur +
intégration sjar, M2 layer applicative, M2b véhicules de lancement et M3 hot reload
in-JVM sont implémentés).

== Séquence de bootstrap runtime

[mermaid]
....
sequenceDiagram
  participant App
  participant Vauban
  participant Loader as ServiceLoader
  participant BM as BeanManager
  participant CTX as Contexts

  App->>Vauban: Vauban.bootstrap()
  Vauban->>Loader: charger BeanFactory<*>\n(via _Factory générés)
  Loader-->>Vauban: liste de _Factory
  Vauban->>BM: instancier VaubanBeanManager
  Vauban->>CTX: ApplicationContext.activate()
  Vauban->>BM: fire @Initialized(Application)
  Vauban-->>App: VaubanContainer
  App->>BM: select(HelloApp.class).get()
  BM->>CTX: Context.get(bean)
  CTX-->>App: instance (proxy si normal-scope)
....

L'`ApplicationContext` est créé en mémoire, sans réflexion, sans ouverture de packages.

[#virtual-threads]
== Modèle de threading

Vauban utilise les **virtual threads** (https://openjdk.org/jeps/444[JEP 444]) pour deux usages :

. **Observateurs asynchrones** — chaque `@ObservesAsync` est dispatché sur un `Executors.newVirtualThreadPerTaskExecutor()` interne au `EventDispatcher`. Pas de pool de threads plateforme, pas de file d'attente bornée.
. **Contexte de requête** — quand Vauban est embarqué dans Cassini ou Foy, le `RequestContext` est porté par un `ScopedValue` (https://openjdk.org/jeps/487[JEP 487]) plutôt qu'un `ThreadLocal`. Cela permet aux virtual threads structurés de propager le contexte sans fuite.

[NOTE]
====
Le passage `ThreadLocal` → `ScopedValue` est documenté dans le `CLAUDE.md` du repo Vauban comme principe directeur.
====

== Compatibilité AOT

Aucun `Class.forName`, aucun `Method.invoke`, aucun `Class.getDeclaredFields()` n'est appelé à chaud. Le runtime utilise :

* des **invocations directes** sur les `_Factory` générés ;
* des **`MethodHandles`** pour l'invocation des `@PostConstruct`, `@PreDestroy`, observateurs et intercepteurs ;
* aucun chargement dynamique de classe au-delà du `ServiceLoader` standard.

Conséquence : Vauban se compile en image native GraalVM sans fichier `reflect-config.json`. Il est compatible avec Project Leyden CDS et avec une image JLink minimale.
