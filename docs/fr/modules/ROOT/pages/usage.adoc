= Cas d'usage
:description: Scopes, qualifiers, producers, événements, intercepteurs, intégration Cassini et Foy.

[.lead]
Cette page couvre les patterns CDI 4.1 Lite supportés par Vauban et leur intégration avec les autres modules de l'écosystème. Tous les exemples se compilent ; le bytecode d'injection est entièrement généré à `process-classes`.

== Scopes

CDI 4.1 Lite couvre quatre scopes. Vauban les supporte tous, plus `@RequestScoped` quand un transport contextuel est branché.

[cols="1,3,1"]
|===
| Scope | Sémantique | Implémenté

| `@Singleton`
| Un seul bean pour la JVM, pas de proxy.
| ✅

| `@ApplicationScoped`
| Un seul bean par container, proxy normal-scope.
| ✅

| `@Dependent`
| Une instance par point d'injection, pas de proxy.
| ✅ (par défaut)

| `@RequestScoped`
| Une instance par requête, proxy normal-scope.
| ✅ (avec Cassini ou Foy actifs)

| `@SessionScoped`
| Une instance par session HTTP.
| // TODO@user: confirmer le statut côté Foy / Cassini
|===

[NOTE]
====
Les scopes normaux (`@ApplicationScoped`, `@RequestScoped`) reçoivent un client proxy `_ClientProxy` généré à la compilation. Le proxy intercepte chaque appel et délègue au contexte actif. Les beans `@Dependent` et `@Singleton` n'en reçoivent pas.
====

=== Beans proxyables et constructeur d'entrée `ProxyLink`

Le client proxy étant une sous-classe du bean, CDI 4.1 déclare certaines classes
_non proxyables_ pour les scopes normaux : classes `final`, classes portant des méthodes
`final` non privées, et classes sans constructeur no-arg non privé. Les membres `final`
sont signalés en erreur (le tissage ne peut pas les corriger) ; le cas du constructeur
manquant — le style courant du constructeur `@Inject` unique — est traité automatiquement :

**Dans tout build basé sur javac (Maven, Gradle, `javac` nu, le montage Vidocq standard),
rien à faire.** Le processeur d'annotations Vauban embarque un plugin javac auto-démarré
qui, à la fin de la compilation, tisse un constructeur d'entrée synthétique `(ProxyLink)`
dans la classe compilée du bean et fait pointer le constructeur du proxy généré dessus.
Votre source ne le déclare jamais. La création du proxy n'exécute alors aucune logique du
bean — ni effets de bord dupliqués, ni `NullPointerException` sur un paramètre `@Inject`
déréférencé. Le `vauban-maven-plugin` applique le même tissage en `process-classes`, en
seconde couche et pour les jars de l'écosystème qui ne passent pas par javac.

**Quand la sortie du build n'est pas tissée** — typiquement un build d'IDE : le
compilateur d'IntelliJ écrit les classes sur disque après la fin de javac, ce qui met le
plugin javac en échec — le container le détecte au démarrage, avant tout chargement de
classe de bean, et attache l'agent `vauban-weaver` à la JVM courante : la même
transformation est appliquée au moment où la classe est définie. Vous verrez un warning
Vauban listant les beans concernés, plus l'avertissement standard du JDK sur les agents
dynamiques ; le comportement est sinon identique à un build tissé. Cet étage se désactive
avec `-Dvauban.weaving.loadtime=disabled`, ou s'évite entièrement dans IntelliJ en cochant
_Delegate IDE build/run actions to Maven_. Voir
xref:internals.adoc#weaving-tiers[Fonctionnement interne — étages de tissage] pour la
mécanique complète.

**Sans aucun étage de tissage**, déclarez vous-même le constructeur d'entrée
(`io.vidocq.vauban.api.ProxyLink`, extension Vauban comparable à la construction
« relaxed » de Weld) :

[source,java]
----
@ApplicationScoped
public class Oidc {
    private final String issuer;

    @Inject
    public Oidc(Config config) {
        this.issuer = config.issuer();
    }

    protected Oidc(ProxyLink link) {   // porte d'entrée du proxy — corps vide
        this.issuer = null;            // javac exige l'assignation des final non initialisés
    }
}
----

Dans les deux cas le proxy chaîne vers ce constructeur (en passant toujours `null`), et le
container ne le sélectionne jamais pour l'injection ni pour instancier le bean. Les
initialiseurs de champs s'exécutent dans tous les constructeurs — gardez-les sans effet de
bord.

== Qualifiers

Permettent de discriminer plusieurs implémentations d'un même type.

[source,java]
----
import jakarta.inject.Qualifier;
import java.lang.annotation.*;

@Qualifier
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.FIELD, ElementType.PARAMETER, ElementType.TYPE})
public @interface Audit {}

@ApplicationScoped @Audit
public class AuditLogger implements Logger { /* ... */ }

@ApplicationScoped
public class Service {
    @Inject @Audit Logger logger;
}
----

`@Named`, `@Default`, `@Any` sont supportés. Les qualificateurs custom avec membres `@Nonbinding` également.

== Producers et `@Disposes`

[source,java]
----
@ApplicationScoped
public class DataSourceProducer {

    @Produces @ApplicationScoped
    public DataSource dataSource(Config config) {
        return DataSource.builder().url(config.url()).build();
    }

    public void close(@Disposes DataSource ds) {
        ds.close();
    }
}
----

Le `@Disposes` est appelé quand le bean producteur est détruit. Vauban génère pour chaque méthode producer une `_ProducerFactory` distincte.

== Événements

[source,java]
----
public record OrderCreated(String id) {}

@ApplicationScoped
public class OrderService {
    @Inject Event<OrderCreated> events;

    public void create(String id) {
        events.fire(new OrderCreated(id));
    }
}

@ApplicationScoped
public class OrderListener {
    public void onOrder(@Observes OrderCreated event) {
        System.out.println("nouvelle commande " + event.id());
    }
}
----

Les observateurs asynchrones (`@ObservesAsync`) sont dispatchés sur l'`Executors.newVirtualThreadPerTaskExecutor()` interne. Voir xref:internals.adoc#virtual-threads[modèle de threading].

== Intercepteurs

[source,java]
----
@InterceptorBinding
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.TYPE, ElementType.METHOD})
public @interface Logged {}

@Logged
@Interceptor
@Priority(Interceptor.Priority.APPLICATION)
public class LoggingInterceptor {

    @AroundInvoke
    public Object around(InvocationContext ctx) throws Exception {
        long t0 = System.nanoTime();
        try {
            return ctx.proceed();
        } finally {
            System.out.printf("%s : %d ns%n", ctx.getMethod(), System.nanoTime() - t0);
        }
    }
}

@ApplicationScoped @Logged
public class Service { /* méthodes interceptées */ }
----

`@AroundConstruct` est également supporté. Les chaînes d'intercepteurs sont résolues à la compilation et stockées dans la `_Factory` générée.

== `Instance<T>` programmatique

[source,java]
----
@ApplicationScoped
public class Router {
    @Inject Instance<Handler> handlers;

    public Handler resolve(String name) {
        return handlers.select(NamedLiteral.of(name)).get();
    }
}
----

`Instance<T>` permet la résolution dynamique côté application, tout en gardant la grille d'injection statique côté container.

== Intégration avec Cassini (Jakarta REST)

`vauban-core` est la couche DI sous-jacente de xref:cassini::index.adoc[Cassini]. Les ressources `@Path` sont des beans CDI ; les providers (`@Provider`, `MessageBodyReader`/`Writer`) également. Pas de configuration : Cassini consomme directement le `BeanManager` Vauban.

[source,java]
----
@Path("/orders")
@ApplicationScoped
public class OrderResource {
    @Inject OrderService service;

    @POST
    public Response create(OrderRequest req) {
        service.create(req.id());
        return Response.created(URI.create("/orders/" + req.id())).build();
    }
}
----

== Intégration avec Foy (Jakarta Servlet)

xref:foy::index.adoc[Foy] expose les servlets, filtres et listeners comme beans CDI. Les `@RequestScoped` suivent le cycle requête/réponse HTTP.

== Tests JUnit avec `@VaubanTest`

[source,java]
----
@VaubanTest
class GreetingServiceTest {
    @Inject GreetingService greeting;

    @Test
    void hello() {
        assertEquals("Hello, Vauban!", greeting.hello("Vauban"));
    }
}
----

L'extension boote un container minimal par classe de test. Voir xref:reference.adoc#junit-extension[la référence JUnit].
