# Vauban: CDI 4.1 Full

Date: 19 October 2026. Code baseline: `52307889` (`origin/main`).

**Decision (19 October 2026): Vauban implements CDI 4.1 Full, the version Jakarta EE Web Profile 11 requires.
CDI 5 is left for later.** CDI 5.0 belongs to Jakarta EE 12, and its API is not a superset of 4.1's: an
implementation built on the 5.0 API would fail the CDI 4.1 signature test and the 4.1 TCK tests that use the removed
methods. This study plans the Full work on 4.1. It builds on two earlier documents:

- `CDI-FULL.md` (Antoine Sabot-Durand, branch `docs/cdi-full-planning`, never merged): which parts of Full fit the
  existing build-time pipeline, and the decision to isolate portable extensions in an opt-in module (§3 below);
- `2026-10-19-cdi-5-full-migration-study.md` (this directory): the Full stages F0–F6 and their estimates, which hold
  for 4.1, and the evidence on the current code.

Tracking: [vauban#38](https://codefloe.com/Vidocq/vauban/issues/38) (Full),
[vauban#39](https://codefloe.com/Vidocq/vauban/issues/39) (portable extensions), and on the runtime side
[vidocq#281](https://codefloe.com/Vidocq/vidocq/issues/281) (groundwork, 1.1.0) and
[vidocq#267](https://codefloe.com/Vidocq/vidocq/issues/267) (Full, 1.2.0), in the release plan of `vidocq/ROADMAP.md`.

## 1. Target

- **CDI 4.1 Full**, core and Java SE contracts first, with the official CDI 4.1 TCK (`cdi.tck.version` 4.1.0) and the
  CDI 4.1 signature test.
- Then the integration the Web Profile needs: sessions and conversations over Foy, EL over Peano, transactional
  observers over Mansart, validated with the TCK groups applicable to a Web Profile container. Which groups those are
  (`integration`, `javaee-full`…) is to confirm against the CDI 4.1 TCK guide; "Full core passes" is never presented as
  a Web Profile certification.
- One engine: `vauban-core` stays the Lite implementation, an optional `vauban-full` module adds Full, with narrow
  hooks in core. An application on Lite never loads `vauban-full`. The engine is kept independent of the CDI API
  version, so CDI 5 remains possible later without redoing Full.

## 2. What CDI 4.1 Full adds over Lite, and where Vauban stands

| Feature | Vauban today (`52307889`) | Fits the build-time pipeline? |
|---|---|---|
| Portable extensions (`Extension`, lifecycle events, configurators) | `VaubanSeContainerInitializer.addExtensions` ignores them; no lifecycle | No: dynamic by design (§3) |
| Full `BeanManager`: `createBean`, `getProducerFactory`, `getInjectionTargetFactory`, `createInterceptionFactory`, `getPassivationCapableBean`… | several methods throw `IllegalStateException(MSG_NOT_IMPLEMENTED)` (`VaubanBeanManager`, from line 455) | Mostly, as API completion; some depend on the deployment model (§4, F1) |
| Decorators (`@Decorator`, `@Delegate`) | `resolveDecorators` returns an empty list (line 591) | Yes: the same shape as interceptor subclasses (`INTERCEPTORS.md`) |
| `beans.xml` contents: `<alternatives>`, `<interceptors>`, `<decorators>`, `<scan>`, `bean-discovery-mode="all"` | `ContainerScanner` finds `beans.xml` (line 244) and reads the discovery mode, not the enablement sections | Yes, at build time for the archives the build sees |
| Specialization (`@Specializes`) | not implemented | Yes |
| Passivation: passivation-capable beans and dependencies, serializable proxies | context storage and bean ids exist; no passivation contract | Yes, with a stable bean identity |
| Conversation scope (`@ConversationScoped`, `Conversation`) | known as a normal scope (`ScopeInfo`), no context behind it | Yes: a context implementation, driven by the web integration |
| EL: `BeanManager.getELResolver()`, `wrapExpressionFactory()` (deprecated in 4.1, still in the API) | both throw `IllegalStateException` (lines 631, 637) | Yes: a resolver over Peano |
| `InterceptionFactory` | throws (line 768) | Yes, for the build-time path; dynamic for extension-supplied types |
| Session scope over Foy | `vauban-webcontexts` on main, driven by `foy-cdi-vauban` (`VaubanWebContextsListener`) | Already done (foy#23, vauban#148) |

The CDI 5 study reports `vauban-webcontexts` as absent from its checkout; it is on `main` (module of the reactor).
Its other code findings (archive identity missing from the bean model, immediate cleanup of invoker dependencies,
raw-name matching in `BceTypeMatcher`) apply to 4.1 unchanged.

TCK today: `vauban-tck-runner` runs the 4.1 TCK with `<excludedGroups>integration,javaee-full,se,cdi-full</excludedGroups>`
(`vauban-tck-runner/pom.xml` line 163), 774 tests, all green. That figure covers Lite only; it is not the expected
Full total.

## 3. Portable extensions: an isolated runtime module (decision of `CDI-FULL.md`, kept)

Portable extensions run third-party code at container boot that can veto types, change metadata, wrap injection
targets and register beans, interceptors, decorators and observers. Their effect cannot be computed at build time in
general. Build Compatible Extensions, which Vauban supports, are the build-time model; translating every portable
extension into one is not a general solution.

- Support lives in an **opt-in module** (inside or beside `vauban-full`, name to settle in F0), not loaded by default.
- Classes for extension-registered beans are generated with the **Class-File API at run time** (the same JDK tool as
  the build-time pipeline, only the timing changes) and loaded with `MethodHandles.Lookup.defineHiddenClass`: no
  ASM, no Byte Buddy, no new dependency.
- `module-info` opens only the packages that need a privileged `Lookup`; never `opens ... to *`. The exception is
  documented in the module's `module-info` Javadoc.
- After a mutation by an extension, generated build-time code for the affected bean may be stale: the deployment
  model (F1) decides, per bean, reuse, regeneration at boot, or the dynamic path. Fast dispatch after boot is kept.
- BCE and portable extensions coexist, with the phase ordering and `@SkipIfPortableExtensionPresent` of the
  specification.

## 4. Stages

The stages and ranges of the CDI 5 study's Full part, applied to 4.1. One engineer familiar with Vauban and CDI;
days include focused tests and review. Re-estimate after F0/F1, as that study asks: a count of unimplemented SPI
methods is not a reliable effort model.

| Stage | Work | Completion gate | Engineer-days | Release |
|---|---|---|---|---|
| F0 | A Full runner on the 4.1 TCK: drop `cdi-full` and `se` from the exclusions where the environment supports them; failure map by TCK requirement; representative portable-extension fixtures | Repeatable failure map, every exclusion justified | 3–5 | 1.1.0 |
| F1 | The deployment and archive model: archives, effective annotations and types, bean attributes, injection points, enablement and visibility, mutable during the extension phases and frozen after validation; the reuse/regeneration rule for generated code | A metadata change made during deployment changes real injection behavior on both paths (generated and startup); archive visibility testable | 8–12 | 1.1.0 |
| F2 | Portable extensions (§3): discovery, lifecycle events, observers, configurators, definition errors; the missing `BeanManager`, `ProducerFactory`, `InjectionTarget` and bean creation operations | An extension adds, vetoes and modifies a type, replaces an injection target, registers beans and observers; invalid changes fail in the right phase | 18–30 | 1.2.0 |
| F3 | `beans.xml` and programmatic enablement, specialization, `InterceptionFactory` | Archive-scoped selection, specialization chains and interception order pass focused tests and their TCK groups | 10–18 | 1.2.0 |
| F4 | Decorators: delegates, generic delegate resolution, ordering, chains combined with interceptors | Several decorators compose with interceptors, producers and extension-modified beans | 6–12 | 1.2.0 |
| F5 | Passivation: passivation-capable beans and dependencies, stable identity, proxy restoration, validation of passivating graphs | Round trips restore working references; illegal graphs fail as required | 10–20 | 1.2.0 |
| F6 | Cross-feature TCK failures; generated paths, Java Modules, lifecycle cleanup, representative third-party extensions; conformance evidence | Every test applicable to the declared Full environment passes, official exclusions only; the CDI 4.1 signature test passes | 10–20 | 1.2.0 |
| W | Web Profile integration: conversation scope and its propagation over Foy sessions, EL over Peano (the deprecated `BeanManager` methods included), transactional observers over Mansart | The applicable integration TCK groups pass in the assembled runtime | 15–35 | 1.2.0 |

Total: **65–120 engineer-days** for F0–F6, **15–35** for W. F1 and F2 are the critical dependency: decorators or
passivation before the effective metadata and the bean identity are settled means rework.

## 5. Validation

1. **Pinned evidence**: revision, Java and Maven versions, dependency graph, TCK release, selection and exclusions
   for every result; never a `BUILD SUCCESS` line as the result.
2. **Both execution paths**: the Arquillian runner exercises startup discovery; add fixtures compiled through the
   processor and the plugin for every Full feature, plus mixed generated and unprocessed dependencies.
3. **CI enforces**: Lite and Full reported separately, failures, errors, missing reports, empty suites and
   unexplained skips fail the pull request (the `ci.tck.modules` gate already runs the Lite and AtInject suites).
4. **Java Modules and lifetimes**: application layers, non-public members, service loading, repeated containers and
   reloads; tests that define classes irreversibly run in both orders; retained class loaders and dependent instances
   tracked after shutdown.
5. **Downstream**: Foy, Cassini, Mansart, the MicroProfile bricks and the Vidocq runtime rebuilt and tested against
   `vauban-full`; Lite applications must not change.
6. **Performance**: cold start, loaded classes, memory, injection and lookup, events and interception compared with
   Lite on the same applications; an application that does not use Full must not pay for it.
7. **Claims**: tested support, the complete applicable TCK result and a formal compatibility listing are three
   different statements.

The first increment is F0: a trustworthy Full failure map on the 4.1 TCK, which makes the rest of the estimate
concrete before the deployment model is built.
